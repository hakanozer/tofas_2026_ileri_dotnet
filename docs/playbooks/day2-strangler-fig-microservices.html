Strangler Fig → Microservice Geçişi: YARP, gRPC, Kafka & Outbox

Gün 1'deki monolith modüllerini Strangler Fig pattern ile bağımsız servislere ayırma. YARP Gateway üzerinden trafik yönlendirme, gRPC inter-service communication, Kafka stream processing ve MassTransit Outbox ile dağıtık tutarlılık. Odak: sıfır downtime geçiş stratejisi, at-least-once semantics, zero-allocation Kafka tüketimi ve saga orkestrasyonu.

🧭 Günün hedefleri

  • Strangler Fig: YARP rotalarını adım adım monolith'ten yeni mikroservislere yönlendirmek.
  • Order Service ↔ Inventory Service arası senkron iletişimi gRPC ile kurmak (Deadline propagation, OTEL span linking).
  • Telemetry Stream Processor'ı Kafka'dan tüketen zero-allocation consumer pipeline olarak çalıştırmak.
  • MassTransit + EF Core Outbox ile transactional event publish ve Saga choreography ayağa kaldırmak.
  • Redis Cache-Aside + Domain Event invalidation pipeline'ını canlı olarak test etmek.

💥 Savaş hikayesi #1 — "Strangler Fig Tuzağı: Header Kaybı"

Senaryo: Kuzey Avrupa lojistik platformunda monolith'ten mikroservise geçiş sırasında YARP üzerinden /api/orders rotası yeni Order Service'e yönlendirildi. İlk 48 saat sorunsuz çalıştı. Sonra "kullanıcı yetkisiz" hataları patladı — ama sadece belirli müşterilerde.

Kök neden: Monolith JWT'yi kendi middleware'inde parse edip X-User-Id header'ı ekliyordu. YARP request transformation kurallarında bu header taşınıyordu — ama monolith'in JWT middleware'i claim içine "tenant_id" koyan özel bir handler'ı vardı. Yeni serviste bu claim yoktu. Belirli müşteriler multi-tenant auth akışı kullanıyordu; diğerleri standart JWT ile çalışıyordu.

Çözüm: (1) YARP'ın RequestTransforms bölümünde eksik header'ları inject eden custom transform yazıldı, (2) monolith ve yeni servis için paylaşılan JWT claim seti bir contract olarak tanımlandı (Shared.Kernel.Grpc), (3) A/B trafik split: %10 yeni servis, %90 monolith → kademeli rollout, (4) integration test: her rotanın multi-tenant token ile test edilmesi zorunlu hale getirildi.

Ders: Strangler Fig'de en büyük risk implicit context kaybıdır. Monolith'te "her yerde erişilebilir" olan bilgi, servis sınırı geçildiğinde explicit olarak taşınmalıdır.

💥 Savaş hikayesi #2 — "Kafka Rebalance Fırtınası"

Senaryo: Telemetri işlemci 3 instance olarak deploy edildi (6 partition, 2 partition/instance). Yeni bir deploy sırasında rolling update yapıldı — yeni pod ayağa kalktıkça eski pod'lar shutdown oldu. Sonuç: 22 dakika boyunca 0 mesaj işlendi.

Kök neden: PartitionAssignmentStrategy default (Range) kullanılıyordu. Her pod değişiminde Kafka tüm partitionları revoke edip yeniden dağıtıyordu (eager rebalance). Rolling update sırasında N-1 pod → N pod → N-1 pod geçişleri sürekli rebalance tetikledi. MaxPollIntervalMs timeout (5 dk) dolmadan yeni consumer geldi → yine rebalance.

Çözüm: (1) CooperativeSticky assignment strategy: sadece taşınan partitionlar revoke edilir, diğerleri çalışmaya devam eder, (2) SessionTimeoutMs 45s'e düşürüldü (faster failure detection), (3) Kubernetes'te maxUnavailable: 0, maxSurge: 1 ile "yeni pod hazır, eski öl" stratejisi, (4) consumer lag metriği Prometheus'a eklendi — rebalance sırasında alarm.

Ders: Kafka consumer group rebalance, production'da en sık karşılaşılan "sessiz veri kaybı" nedenidir. CooperativeSticky .NET 10'da varsayılan DEĞİLDİR — explicit set edilmelidir.

💥 Savaş hikayesi #3 — "Outbox Table Bomba Gibi Patladı"

Senaryo: MassTransit EF Core Outbox ile production'a çıkıldıktan 3 ay sonra PostgreSQL disk %97'ye ulaştı. outbox.outbox_message tablosu 142 milyon satıra ulaşmıştı. RabbitMQ'ya deliver edilen mesajlar outbox'tan silinmiyordu.

Kök neden: MassTransit outbox delivered mesajları otomatik silmez. InboxState tablosu da deduplikasyon için mesaj hash'leri biriktiriyordu. Cleanup job (BusOutboxOptions.MessageDeliveryTimeout) konfigüre edilmemişti.

Çözüm: (1) MassTransit'in BusOutboxOptions cleanup ayarları aktifleştirildi, (2) PostgreSQL partitioned table ile outbox_message günlük partition'lara bölündü (PARTITION BY RANGE (created_at)), (3) 30 günden eski partition'lar DROP PARTITION ile temizlendi (DELETE yerine — 1000x hızlı), (4) pg_cron ile otomatik partition maintenance.

Ders: Her outbox implementasyonu bir "yazma-optimized" tablodur. Cleanup stratejisi olmadan disk bombasıdır. Partition-by-time en etkili çözümdür.

  5. ÖĞLEDEN SONRA GC baskısı karşılaştırma — Anti-pattern vs Golden Code

    İki consumer implementasyonunu karşılaştır:

    // ❌ ANTI-PATTERN: Her mesajda string allocation
while (true)
{
    var result = consumer.Consume(ct);
    var json = Encoding.UTF8.GetString(result.Message.Value); // string alloc!
    var payload = JsonSerializer.Deserialize<TelemetryPayload>(json); // another alloc!
    await ProcessAsync(payload);
    consumer.Commit(result);  // sync commit per message — throughput killer
}
    // ✅ GOLDEN CODE: ArrayPool + Span + Channel batching
var rented = _pool.Rent(kafkaValue.Length);
kafkaValue.AsSpan().CopyTo(rented.AsSpan());
var payload = TelemetryPayload.DeserializeFromUtf8(rented.AsSpan(0, kafkaValue.Length));
batch.Add(payload);  // batch → Channel → async commit

    dotnet-counters monitor ile GC koleksiyonlarını karşılaştır:

  --counters System.Runtime[gc-gen0-count,gc-gen1-count,gc-gen2-count,gc-heap-size]

⚠️ Gotcha (tuzak) uyarıları

Kafka: CooperativeSticky zorunludur

Confluent.Kafka 4.3.1'de PartitionAssignmentStrategy varsayılanı hâlâ Range'dir. Range stratejisi her rebalance'da tüm partitionları revoke eder — rolling deploy sırasında mesaj işleme tamamen durur. CooperativeSticky explicit set edilmelidir.

PartitionAssignmentStrategy = PartitionAssignmentStrategy.CooperativeSticky
Kafka: EnableAutoCommit = false + StoreOffset + Commit sırası

StoreOffset() sadece "bu offset'i işledim" der, Commit() stored offset'leri Kafka'ya yazar. StoreOffset olmadan Commit çağırırsanız hiçbir şey commit edilmez — consumer restart'ta tüm mesajları tekrar işler. Tam tersi: StoreOffset yapıp Commit unuttusanız aynı sonuç.

ArrayPool<byte>.Return — unutursanız LOH patlar

Pooled buffer'lar ReturnBuffers() ile havuza iade edilmelidir. İade edilmeyen buffer'lar pool'u tüketir; pool bitince yeni allocation GC heap'e düşer. 85KB üzeri buffer'lar LOH'a (Large Object Heap) gider → Gen2 GC fırtınası → p99 latency spike.

// ✅ DOĞRU: finally bloğunda iade
try { await store.BulkUpsertAsync(batch.Items, ct); }
finally { batch.ReturnBuffers(); }

// ❌ YANLIŞ: Exception'da iade unutulur
await store.BulkUpsertAsync(batch.Items, ct);
batch.ReturnBuffers(); // Exception olursa buraya gelmez!
MassTransit Outbox: EF Core Retry ile çakışma

EF Core'un EnableRetryOnFailure() aktifken MassTransit outbox transaction retry'ı = duplicate mesaj. EF retry'ı SaveChanges'i tekrarlar, ama MassTransit zaten kendi retry'ını yapar. İkisi çakışınca aynı mesaj iki kez outbox'a yazılır. Çözüm: EF retry'ı devre dışı bırak, MassTransit retry'ına güven.

MassTransit: CorrelationId eksikliği = sessiz mesaj kaybı

Saga event correlation'ında CorrelateById kuralı tanımlanmazsa MassTransit mesajı sessizce drop eder — hata logu yok, exception yok. Debugging nightmare. Her event'te CorrelationId property'si zorunlu olmalı.

gRPC Deadline: UTC zorunluluğu

CallOptions.Deadline UTC DateTime bekler. DateTime.Now.AddSeconds(5) kullanırsanız local time zone farkından dolayı deadline anında expire olabilir (veya 3 saat sonra expire olur — TR: UTC+3). Her zaman DateTime.UtcNow.AddSeconds(5) kullanın.

Redis KEYS komutu: Production'da yasak

Cache invalidation'da pattern-based temizlik için KEYS inventory:* kullanmayın — O(N) ve Redis'i bloklar. SCAN cursor-based, non-blocking alternatiftir. StackExchange.Redis'te server.KeysAsync(pattern:) SCAN kullanır.

Channel<T> BoundedChannelFullMode.Wait vs DropOldest

Wait: producer (Kafka poll) durur, consumer lag yükselir — veri kaybı yok. DropOldest: producer asla bloklanmaz ama eski mesajlar sessizce kaybolur. Telemetri için Wait doğru seçimdir — business-critical olmayan metric verisi için DropOldest düşünülebilir.
