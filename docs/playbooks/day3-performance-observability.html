Performans & Observability: Span<T>, OTEL, Redis & Sentry

Gün 2'de kurduğumuz pipeline'ı ölçülebilir hale getiriyoruz. Zero-allocation hot-path (Span<T>, Pipeline<T>, ArrayPool), GC modu seçimi, OpenTelemetry trace/metric/log üçlüsü, Redis L1/L2 stampede savunması ve Sentry/Graylog ile production debugging. Odak: p99 latency, GC pause, metric cardinality ve "neden yavaş?" sorusunun kanıtla cevaplanması.

  • GC modu (Server vs Workstation, Concurrent, DATAS) kararını ölçümle vermek; LOH/POH davranışını görmek.
  • OpenTelemetry: ActivitySource + Meter + Serilog ile trace/metric/log korelasyonu (trace_id → Graylog).
  • Sampling stratejisi (head vs tail) ve metric cardinality bombasını önlemek.
  • Redis Cache-Aside'te stampede + L1/L2 tutarlılığını IDistributedLock ve Pub/Sub ile savunmak.
  • Sentry (exception + release + breadcrumb) ve Graylog (GELF structured log) ile prod debugging akışı kurmak.

💥 Savaş hikayesi #1 — "Gen2 GC Fırtınası: p99 Latency Çivisi"

Senaryo: Telemetri işlemci, 40k msg/sn'de 3 ay sorunsuz çalıştı. Filo büyüyünce yük 90k msg/sn'ye çıktı. p99 latency 8ms'den 340ms'ye fırladı; bazı dakikalarda consumer lag 2M mesaja ulaştı. CPU %40, bellek %70 — "kaynak yok" gibi görünmüyordu.

Kök neden: Hot-path'te her mesaj için 3 allocation vardı: Encoding.UTF8.GetString() (string), JsonSerializer.Deserialize (nesne grafiği), ve geofence kontrolünde List<double>. Mesaj başına ~9KB toplam; 90k/sn = ~810 MB/s allocation rate. Bu, LOH'u (85KB+) tetikliyordu ve Gen2 blocking GC saniyede birkaç kez ~200ms pause yapıyordu. dotnet-counters'da gc-gen2-count ve time-in-gc doğrudan kanıtı verdi: time-in-gc %38.

Çözüm: (1) ReadOnlyMemory<byte> + Utf8JsonReader ile zero-alloc parse, (2) geofence kontrolünde stackalloc/Span<double>, (3) ArrayPool<byte>.Shared + finally iade, (4) DOTNET_gcServer=1 ve DOTNET_GCHeapHardLimit ile Server GC. Sonuç: allocation rate ~0, p99 = 6ms, Gen2 GC ~saatte bir.

Ders: "Kaynak yetiyor" hiçbir şey ifade etmez. Allocation rate latency'nin görünmez katilidir. Ölçüm olmadan micro-optimization yapmak = kumar.

💥 Savaş hikayesi #2 — "Prometheus'u Kendi Metriğimizle Vurduk"

Senaryo: Ekip, "her istekte sipariş durumunu görmek istiyoruz" diyerek bir counter ekledi: orders_processed_total{order_id, sku, customer_id}. 2 hafta sonra Prometheus OOM ile crash loop'a girdi; Grafana panelleri dakikalarca yüklenmedi.

Kök neden: Prometheus her benzersiz label kombinasyonu için ayrı bir time series tutar. order_id (uuid) ve customer_id unbounded cardinality üretti: 2 haftada ~120 milyon time series. Bu bir "metric" değil, gizli bir log tablosuydu.

Çözüm: (1) Label'lardan tüm unbounded değerler (uuid, sku, customer) çıkarıldı; yerine status, region gibi sonlu (bounded) boyutlar kondu, (2) yüksek-cardinality ihtiyaç için exemplar (trace_id) kullanıldı — metrikten Jaeger trace'ine atlama, (3) Prometheus'ta metric_relabel_configs ile "drop" guard'ı, (4) eğitimde "cardinality budget" kuralı: her servis toplam <5000 aktif series.

Ders: Metrik ve log farklı araçlardır. Bir metrik label'ına sınırsız değer koyuyorsanız, aslında metrik değil log üretiyorsunuz — ve storage'ı öldürüyorsunuz. Exemplar, "hangi istek?" sorusunun doğru cevabıdır.

💥 Savaş hikayesi #3 — "Redis Sustu, Sistem Çöktü (Cache'i Kritik Yaptık)"

Senaryo: Redis master failover sırasında 40 saniye erişilemez oldu. Inventory API, cache miss'te DB'ye gitti — ama aynı anda binlerce istek gitti (stampede). PostgreSQL connection pool (100) anında tükendi; NpgsqlException: The connection pool has been exhausted. Order akışı dahil tüm sistem durdu.

Kök neden: İki anti-pattern: (1) Cache kritik bağımlılık haline gelmişti — Redis down olunca tüm trafik DB'ye yüklendi (cache-aside'ın "cache yoksa handler'a düş" davranışı doğru, ama thundering herd korumasızdı), (2) Cache-aside behavior'da in-memory L1 yoktu; her hit bir network round-trip.

Çözüm: (1) IDistributedLock (Redis RedLock) ile "single-flight": key başına tek istek DB'ye gider, diğerleri bekleyip cache'ten okur, (2) kısa-TTL L1 in-memory cache (stale-while-revalidate), (3) abortConnect=false + circuit breaker: Redis down iken istekleri hızlı fail edip DB'yi koru, (4) DB connection pool limiti + Timeout metriği alert'e bağlandı.

Ders: Cache'i "performans" için eklersiniz, ama yanlış yapılandırırsanız kritik bağımlılık haline gelir. Cache-aside + stampede koruması + circuit breaker üçlüsü ayrılmaz parçadır.

  3. SABAH Kriz senaryosu: Anti-pattern vs Golden Code (hot-path)

    Önce kasıtlı anti-pattern'i göster:

    // ❌ ANTI-PATTERN — her mesajda 3 allocation
var json = Encoding.UTF8.GetString(kafkaValue);          // 1) string
var payload = JsonSerializer.Deserialize<TelemetryPayload>(json); // 2) nesne grafiği
var geofence = new List<double> { payload.Latitude, payload.Longitude }; // 3) LOH adayı
await ProcessAsync(payload);

    Sonra Span<T> tabanlı çözümü uygula — Models/TelemetryPayload.cs zaten DeserializeFromUtf8(ReadOnlySpan<byte>) sunuyor:

    // ✅ GOLDEN CODE — sıfır heap allocation (hot path)
void OnMessage(ReadOnlySpan<byte> value)
{
    // Utf8JsonReader ref struct'tır → heap'e kaçmaz
    var point = TelemetryPayload.DeserializeFromUtf8(value);

    // Geofence kontrolü → stackalloc (LOH yok)
    Span<double> coord = stackalloc double[2];
    coord[0] = point.Latitude;
    coord[1] = point.Longitude;

    if (GeofenceIndex.Contains(coord))     // Span alan overload
        _agg.Add(in point);
}

    dotnet-counters'da alloc-rate ve gen-0-size tekrar oku — Lab 1 baseline'ı ile karşılaştır.

  4. SABAH DaTAS / POH — pinned object heap farkı

    Büyük, uzun ömürlü (sık pinlenen) buffer var mı? POH'u göster:

    # POH (Pinned Object Heap) kullanımı
readonly static byte[] s_scratch = GC.AllocateArray<byte>(1024 * 1024, pinned: true);

# Runtime event ile POH allocation doğrula
dotnet-trace collect --process-id <PID> --providers Microsoft-Windows-DotNETRuntime:0x1:5
# trace'i PerfView / dotnet-trace report ile aç → GCAllocationTick, PinnedObjectHeap

    Tartışma: stackalloc ne zaman tehlikeli? (Cevap: >~1KB veya döngü içi → stack overflow. Büyük buffer → ArrayPool. Sık pinlenen ve büyüyen → POH.)

⚠️ Gotcha (tuzak) uyarıları

Span<T> / ref struct: async ve field yasağı

Span<T>, ReadOnlySpan<T> ve Utf8JsonReader birer ref struct'tır. async metotta local olarak tutulamaz (state machine'e giremez), class field olamaz, Task içinde await sonrası kullanılamaz. Ayrıca bir lambda/closures içine capture edilemez. Hot-path'i senkron tut; async gerekiyorsa ReadOnlyMemory<T> kullan.

stackalloc: >1KB = StackOverflowException

stackalloc thread stack'ten yer alır (varsayılan ~1MB). Döngü içinde veya >~1KB için kullanmayın — StackOverflowException yakalanamaz, process anında ölür. Büyük/yeniden kullanılan buffer → ArrayPool<T>. Sık pinlenen + büyük → GC.AllocateArray(pinned: true) (POH).

ActivitySource: Dispose etmek ve listener olmaması

ActivitySource'ı static tutun, Dispose etmeyin. Hiçbir listener (OTEL SDK) yoksa StartActivity() null döner — bu yüzden activity?.SetTag(...) gibi null-conditional kullanın. Ayrıca .AddSource("...") ile kaynak adını tam eşleşmeyle kaydetmezseniz span'lar sessizce üretilmez.

Metric cardinality bombası

Metrik label'ına order_id/sku/user_id gibi unbounded değer koymayın. Her benzersiz kombinasyon ayrı time series'tir; Prometheus OOM'a gider. "Hangi istek?" sorusu için exemplar (trace_id) kullanın — metrikten Jaeger trace'ine atlama. Eğitimde kural: servis başına <5000 aktif series.

OTEL exporter kapanışı — son span'ler kaybolmasın

Uygulama SIGTERM ile kapanırken batch exporter kuyruğu flush edilmezse son span/log'lar kaybolur. ASP.NET Core'da AddOpenTelemetry().WithTracing(...) hosted service ile flush eder; ama worker/console uygulamalarda TelemetryConfiguration/TracerProvider'ı Dispose veya ForceFlush çağırın. Graceful shutdown süresi (K8s terminationGracePeriodSeconds) yeterli olmalı.

ArrayPool: return unutulursa sessiz sızıntı

ArrayPool<byte>.Shared iade edilmeyen buffer'ları asla geri almaz; pool boşalınca her istek yeni new byte[] üretir → hedeflediğin "zero-alloc" kaybolur. Her zaman try/finally ile Return(array, clearArray: false). Ayrıca pool'dan gelen buffer sıfırlanmış değildir — eski veri kalabilir (gizlilik + parse hataları).

Redis: IConnectionMultiplexer singleton + KEYS yasağı

ConnectionMultiplexer.Connect'i bir kez yapın ve DI singleton olarak paylaşın — her istekte yenisi = socket+ağ patlaması. Pattern invalidation'da KEYS inventory:* kullanmayın (O(N), Redis'i bloklar); server.KeysAsync(pattern:) (SCAN tabanlı) kullanın. Ama SCAN de tüm keyspace'i tarar — milyonlarca key'de namespace tasarımı yapın.

Server GC container'da memory limitini aşar

DOTNET_gcServer=1 her çekirdek için ayrı heap segmenti ayırır. 8 çekirdekli bir container'a 1GB limit verirseniz GC, heap'i büyütmeye çalışırken OOMKilled olursunuz. DOTNET_GCHeapHardLimit (ör. 0x40000000=1GB) veya Kubernetes'ta GOMEMLIMIT benzeri limit ile GC'yi sınırlayın — aksi halde container, sınırı bilmeden ölür.

Serilog double-write & PII

Console + GELF aynı anda yazmak CPU/IO overhead ve log kopyası demektir; prod'da MinimumLevel.Override ile framework log'larını kısın. Daha kritik: structured log'a Authorization header, JWT, TCKN, kart no sızabilir — Destructure.ByTransforming/WithSensitiveDataMasking ile maskeleme zorunlu.

Sentry: PII ve event hacmi

Varsayılan SendDefaultPii=false olsa da Request body/cookie ve breadcrumb'lar veri taşır. SetBeforeSend ile scrub edin. Ayrıca her 4xx için exception göndermeyin (validation hataları) — Sentry'yi gürültüye boğar, gerçek regresyonu gizler. TracesSampleRate düşük tutun (ör. 0.1).

Ölçmeden optimize etmek

Bu günün tek kuralı: baseline ölç, sonra değiştir, sonra tekrar ölç. dotnet-counters (canlı), dotnet-trace (event), dotnet-gcdump/dotnet-dump (post-mortem) araçlarını göster. "Micro-optimization" sezgisi prod'da yanıltır; allocation profili dotnet-trace + PerfView/Speedscope ile kanıtlanır.
