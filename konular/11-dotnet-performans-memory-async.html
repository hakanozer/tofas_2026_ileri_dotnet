Memory management: tahsis etmemek değil, ömrü kontrol etmek

GC managed heap'teki canlı nesneleri izler ve erişilemeyenleri toplar; high allocation rate, Gen 0/1 toplama sıklığını; uzun ömürlü referanslar, promotion/Gen 2 baskısını; büyük contiguous object'ler LOH davranışını etkiler. “GC pahalıdır” genellemesi yerine allocation bytes/op, Gen2/LOH, pause time, working set ve request latency ölçün. Pooling, nesneyi tekrar kullanırken state temizliği ve eşzamanlı ownership disiplinini geliştiriciye yükler.

Span<T>/ReadOnlySpan<T> contiguous memory üzerinde stack-only view sunar; slicing/parsing sırasında ara array/string tahsisini azaltır. Heap'e konamaz, boxing/async sınırları vardır ve ref struct yaşam kuralları compiler tarafından denetlenir. Memory<T> heap'te saklanabilen async-friendly view'dur; ama underlying buffer'ın geçerliliğini ve sahipliğini kendi başına garanti etmez. Performans için tüm kodu Span'a çevirmek yerine profiler'da sıcak path belirleyin.

static bool TryReadHeader(ReadOnlySpan<byte> packet, out int version)
{
    version = 0;
    if (packet.Length < 2) return false;
    version = packet[0];
    return packet[1] == 0xA5;
}

Async/await: thread'i bekletmeyin, kapasiteyi yine sınırlayın

I/O-bound async operation thread'i bloklamadan tamamlanmayı bekler; CPU-bound hesaplama CPU ve worker thread kullanır. .Result/.Wait() thread pool starvation ve sync-over-async deadlock yaratabilir. Her async zincirde cancellation, exception ve deadline propagate edilmelidir. Task.Run web request içindeki blocking DB çağrısını non-blocking yapmaz; yalnızca thread'i başka queue'ya taşır. Unbounded async task başlatmak da DB pool ve remote quota'yı aşırı yükleyebilir.

Channel<T>, process içi producer-consumer koordinasyonu ve bounded capacity ile backpressure için kullanışlıdır. In-memory channel process çökünce mesajı kaybeder; durable broker yerine geçmez. SingleWriter/SingleReader seçenekleri doğruysa optimizasyon sağlayabilir, yanlışsa data race/bozuk concurrency ortaya çıkar. FullMode=Wait producer'ı yavaşlatır; DropOldest/DropWrite veri kaybı kabul edilen telemetry gibi senaryoda açık politika ile kullanılabilir.

Repo'da gerçek throughput örneği

KafkaTelemetryConsumer, Kafka'dan byte[] alıp ArrayPool<byte> ile buffer kiralıyor, Span<byte> üzerinde deserialization yapıyor ve batch'i bounded Channel<PooledTelemetryBatch>'a iletiyor. Capacity dolduğunda Wait, consumer polling loop'unda doğal backpressure oluşturuyor. TelemetryBatchProcessor buffer'ları finally içinde geri iade ediyor.

Rented buffer'ın logical length ile array.Length'i karıştırmayın; pool daha büyük array döndürebilir. Sensitive payload varsa iade öncesi clear etme gereksinimini değerlendirin; clearing CPU maliyetlidir. Buffer'ı birden çok processor'a paylaşmak veya ReturnBuffers'tan sonra okumak use-after-return ve veri bozulmasına neden olabilir. Channel queue length, waiting time, pooled bytes ve Kafka consumer lag birlikte ölçülmelidir.

Hata ve kapasite senaryoları

  • Processor DB'ye yetişemiyor: bounded queue dolumu lag'i yükseltir; scaling/DB kapasitesi/partition dengesi incelenir.
  • Mevcut consumer'da doğrulanmış veri kaybı riski: FlushBatchAsync batch'i in-memory Channel'a yazdıktan hemen sonra StoreOffset/Commit yapıyor; Npgsql store kalıcı yazımı daha sonra processor'da çalışır. Commit'ten sonra process çöker veya BulkUpsertAsync başarısız olursa broker offset'i ilerlemiş, DB'ye yazılmamış batch yeniden teslim edilmeyebilir. Bu nedenle koddaki “at-least-once” yorumu mevcut akış için geçerli bir garanti değildir.
  • TelemetryBatchProcessor persistence exception'ını loglayıp devam ediyor; durable retry/DLQ yoksa buffer'ı iade etmek mesajı kurtarmaz. Bu kod production loss policy olarak alınmamalıdır.
  • Güvenli düzeltme yalnızca commit satırını başka threade taşımak değildir: Kafka consumer API'sinin thread-affinity'si, birden çok processor'ın eşzamanlılığı, her partition'da contiguous persisted offset, graceful shutdown ve rebalance birlikte çözülmelidir. Örneğin poll thread'ine başarı onayı geri kuyruğu gönderip partition offset'lerini sıralı takip edin; commit'i yalnızca kalıcı sink işlemi başarıyla tamamlanmış kesintisiz aralığa kadar ilerletin. Alternatif olarak her kaydı/batch'i durable, idempotent bir staging store'a yazdıktan sonra commit edin.
  • Cancellation sırasında channel'da kalan batch'ler drain ediliyor mu? Graceful shutdown süresi, offset commit ve buffer cleanup protokolü tanımlanmalıdır.

Kod yürüyüşü: Kafka'dan bounded Channel'a, pooled buffer'a

Telemetry ingest, tek tüketici döngüsünün deserialize işini bounded Channel<T> üzerinden parallel batch writer'lardan ayırır. Bounded capacity bellek üst sınırına yardım eder; channel dolunca Wait back-pressure uygular ve consumer lag büyür. Bu, kapasite sorununun yok olması değil, sınırlı bellekte görünür hale gelmesidir.

// TelemetryBatchProcessor.cs — gerçek tüketim ve buffer ömrü
await foreach (var batch in consumer.Reader.ReadAllAsync(ct))
{
    try
    {
        await store.BulkUpsertAsync(batch.Items, ct);
    }
    catch (Exception ex) when (ex is not OperationCanceledException)
    {
        logger.LogError(ex, "Failed to process batch of {Count}", batch.Items.Length);
        // Eğitim örneği loglayıp devam ediyor; üretimde DLT/replay gerekir.
    }
    finally
    {
        batch.ReturnBuffers();
    }
}

ArrayPool<byte> ile kiralanan buffer'ı her başarı/hata yolunda iade etmek gerekir; aksi halde havuz kaçak allocation ve LOH/Gen2 GC basıncına yol açar. Slice'ın mantıksal uzunluğu kapasite değil, payload uzunluğudur. Span<T> senkron parse penceresidir; async sınırdan taşınacaksa Memory<T> kullanın.

[Consumer](../src/Services/Telemetry/TelemetryStreamProcessor/Kafka/KafkaTelemetryConsumer.cs), [batch processor](../src/Services/Telemetry/TelemetryStreamProcessor/Processing/TelemetryBatchProcessor.cs) ve [worker concurrency](../src/Services/Telemetry/TelemetryStreamProcessor/Worker.cs) birlikte incelenmeli. Kritik hata penceresi: Kafka offset kodda DB batch yazımından önce commit ediliyor; store hatası loglanıp batch düşerse veri kaybı olabilir. Buffer iadesi bellek yönetimidir, mesaj teslimat garantisi değildir.

Profiling ölçütleriThroughput tek başına yeterli değil: allocations/op, Gen2/LOH, GC pause, batch latency p95/p99, channel backlog, Kafka lag, DB write duration ve dropped batch sayısını birlikte izleyin.

Tartışma

Bir 100 KB/saat telemetry trafiği değil, saniyede yüz bin kayıt ölçeğinde allocation/DB throughput'u modelleyin. Aynı sayıda kayıt için 1 KB payload, GC pressure, batch size ve DB write amplification'ı nasıl değiştirir? Benchmark/profiler olmadan pooling kazancı varsayılmamalıdır.

  • ArrayPool'a buffer iade edilmezse ne kadar sürede allocation/LOH baskısı belirginleşir?
  • Channel capacity büyütmek throughput'u mu, yoksa yalnızca gecikmeyi ve bellek kullanımını mı artırır?
  • Telemetry'de kayıp kabul edilirse hangi kalite alanı/cihaz türü için kabul edilir; kritik sipariş event'inde neden aynı karar verilemez?
