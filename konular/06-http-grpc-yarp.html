REST mi, gRPC mi?

HTTP API'leri tarayıcı/partner uyumluluğu, kolay inspect edilebilir JSON, cache ve geniş araç ekosistemi için güçlü varsayılandır. API semantiğinde idempotency, status code, pagination ve problem details açıkça tanımlanmalıdır. gRPC, HTTP/2 üzerinde Protobuf ile tipli sözleşme, küçük binary mesaj ve streaming sağlar; service-to-service, yüksek çağrı hacmi veya istemci/sunucu codegen'inin değerli olduğu yerde uygundur. Gateway/browser erişimi gRPC-Web veya transcoding gerektirebilir. İkisini de “hızlı” oldukları için seçmeyin: gerçek payload ve latency profili ölçülmelidir.

Protobuf alan numaraları wire contract'tır: alan silinse bile numarasını yeniden kullanmayın; deprecated alanı reserve edin; optional/default ve enum evrimini eski/yeni client-server kombinasyonlarında test edin. Büyük mesaj limitleri, deadline, cancellation, metadata propagation ve auth interceptor davranışı da contract'ın parçasıdır.

YARP: edge routing, uygulama logic'i değil

Gateway Program.cs, YARP'ı configuration'dan kuruyor ve reverse-proxy pipeline'a route-aware rate limiting middleware ekliyor. Kod yorumundaki kritik ayrıntı: IReverseProxyFeature proxy endpoint pipeline'ında oluşur; route metadata isteyen middleware'in ana ASP.NET pipeline'ına konması hatalı olabilir. Middleware sırası da önemlidir: authentication ve claim propagation, PII maskesi, token quota ve proxy çağrısı.

Gateway TLS termination, route selection, merkezi edge policy, correlation başlığı ve coarse-grained throttling için yararlıdır. Domain authorization'ın tek kopyası olmamalı; servis kendi kaynak yetkisini doğrulamalıdır. Gateway'i orchestration, veritabanı erişimi veya tüm servisler için tek hata noktası haline getirmeyin. N katmanlı gateway yerine istemci tipi/iş akışına göre BFF gerekebilir. Health, config reload, upstream timeout ve circuit-breaker politikası deployment modelinde test edilmelidir.

Sürüm notuREADME'deki “YARP 3.12.1” ifadesi ile gateway csproj'deki paket sürümü (Yarp.ReverseProxy 2.3.0) farklıdır. Eğitimde gerçek referans için project file'a bakın; preview/gelecek sürümü çalışan paket gibi sunmayın.

Deadline, retry ve hata semantiği

Her outbound çağrıya üst iş akışından türeyen deadline koyun; servis içi timeout toplam request bütçesini aşmamalı. CancellationToken HTTP, gRPC ve DB'ye aktarılmalıdır. Retry sadece geçici hata, idempotent işlem veya deduplication key ile güvenlidir. Gecikmeyi timeout'tan önce ölçün; aynı çağrı zincirinde gateway, HttpClient ve SDK'nın bağımsız retry'leri çarpılarak yükü büyütebilir. gRPC Unavailable retry'ı, server işlemi yapmadı anlamına gelmeyebilir; idempotency key veya operation status sorgusu tasarlayın.

gRPC extension channel için HTTP/2 bağlantısı, connection idle timeout ve gRPC retry policy kaydediyor; interceptor client metadata/deadline konvansiyonları taşıyor. Retry policy tek başına backoff bütçesi, server pushback, retry throttling, per-call idempotency ve telemetry sağlamaz. Ayrıca channel'ı her request'te yaratmak bağlantı havuzlamasını bozar.

Kod yürüyüşü: YARP route'u ile gRPC client politikasını izleyin

Bu repoda gateway route'ları JSON'da tutulur; gRPC interceptor ve retry policy ise ortak building block içinde client pipeline'a eklenir. Bunlar iki farklı ağ sınırıdır: YARP dış HTTP isteğini upstream host'a proxy eder; gRPC client kodu servisler arası tipli RPC çağrısı için channel/call invoker üretir.

// yarp.json'dan gerçek route/transform kesiti
"inventory-api": {
  "ClusterId": "inventory-cluster",
  "Match": { "Path": "/api/inventory/{**catch-all}" },
  "Transforms": [{ "PathRemovePrefix": "/api/inventory" }]
}
// Shared.Grpc — retry yalnız belirlenen geçici status'larda
RetryPolicy = new RetryPolicy
{
    MaxAttempts = 3,
    InitialBackoff = TimeSpan.FromMilliseconds(100),
    MaxBackoff = TimeSpan.FromSeconds(2),
    BackoffMultiplier = 1.5,
    RetryableStatusCodes = { StatusCode.Unavailable, StatusCode.DeadlineExceeded }
};

Retry-attempt sayısı üst seviye request deadline'ına sığmalı; gRPC cancellation token ve deadline aşağı akışa aktarılmalıdır. Read-only çağrı retry'e daha elverişlidir; command tekrarı için idempotency key veya deduplication gerekir. Projedeki [GrpcPipelineExtensions](../src/BuildingBlocks/Shared.Grpc/DependencyInjection/GrpcPipelineExtensions.cs) HTTP/2 bağlantı yönetimi, interceptor ve retry'ı kurar; [YARP config](../src/Gateway/ApiGateway/yarp.json) route/path transform'u tanımlar.

Önemli sınır: Inventory API'de gRPC client/server pipeline kaydı var ama MapGrpcService ve service implementation yok; YARP route'larının bazı backend business endpoint'leri de henüz tamamlanmış değil. Route bulunması canlı endpoint kanıtı değildir. Her çağrı için HTTP/2/TLS, auth metadata, trace propagation, max message, timeout ve compatibility testi ayrı doğrulanmalıdır.

Sunumda gösterinBir client çağrısını (1) client deadline, (2) interceptor metadata, (3) gateway route transform, (4) backend service handler sırasıyla tahtada çizin. Browser'ların gRPC/HTTP2 kısıtını ve gRPC-Web ihtiyacını REST alternatifiyle karşılaştırın.

Tartışma

YARP route config'ini açın; aynı endpoint'in direct service erişimi ve gateway üzerinden erişimi arasındaki auth header, correlation ve timeout farklarını anlatın. Sonra gRPC retry ile command'in iki kez uygulanması olasılığını request sequence üzerinden gösterin.

  • Edge auth doğrulaması başarılı, servis erişim kontrolü atlandı: hangi güven sınırı ihlal edildi?
  • İşlem 1.2 saniyede tamamlanıyor ama client deadline 1 saniye: retry yapmak mı, status endpoint mi?
  • REST endpoint'inin cache-control ve idempotency semantiği hangi consumer'lardan etkilenir?
