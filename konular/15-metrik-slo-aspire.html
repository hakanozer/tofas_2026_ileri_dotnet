Metric, kullanıcı taahhüdüne nasıl bağlanır?

SLI ölçülebilir servis niteliğidir (ör. başarılı ve deadline içinde tamamlanan valid request oranı); SLO iç hedef; SLA müşteriyle sözleşmesel yükümlülük ve muhtemel ceza içerir. SLO, “%99.9 availability” yazmaktan ibaret değildir: eligible traffic, window, numerator/denominator, dependency failure attribution, latency threshold ve maintenance policy belirlenmelidir. Error budget, SLO'yu aşmadan tolere edilebilen failure miktarıdır; ürün yayını ve reliability yatırımı kararına bağlanır.

Request count, error count, latency histogram ve in-flight request (RED) servis trafiğini; saturation (CPU, memory, thread pool, connection pool, queue lag) kapasiteyi açıklar. Histogram bucket'ları p95/p99 için uygun dağılımı yakalamalıdır. Counter monotonic, gauge anlık seviye, histogram örnek dağılımıdır. Tenant/user/order ID'yi metric label'a koymayın; high-cardinality backend memory ve query performansını tüketir.

Health check ≠ monitoring ≠ SLO

Liveness: process yeniden başlatılsa iyileşecek kadar canlı mı? Readiness: yeni trafik almaya hazır mı (gerekli dependency/başlangıç işlemi)? Startup probe: uzun başlayan servise liveness'i erken uygulayıp sürekli restart etmemek için. Her dependency kesintisinde liveness false yapmak restart storm yaratabilir. Readiness'ten DB'yi çıkarıp “service ready” dönmek de downstream timeout'larını sadece bir sonraki hop'a taşır; critical/non-critical dependency kararını açıkça belirleyin.

Mevcut Order, Inventory ve AI API'de basit /health GET endpoint'i var; AddHealthChecks tabanlı liveness/readiness ayrımı ve dependency check örneği solution'da tamamlanmış değildir. Compose bazı altyapılara container healthcheck koyuyor, ancak container startup healthy olması uygulamanın iş kabulüne hazır olduğunun kanıtı değildir.

.NET Aspire: distributed application'ın local modellemesi

Aspire, AppHost ile servisleri, database, queue ve cache gibi kaynakları kod olarak modelleyen; local development orchestration, service discovery/config, dashboard ve telemetry deneyimi sağlayan bir .NET platformudur. Bir production scheduler, cloud provider veya Kubernetes'in yerine geçmez. Geliştirme modelini üretim deployment hedefiyle uyumlu tutabilir, ama deploy pipeline/secret/availability/topology kararlarını otomatik çözmez.

Bu repository'de AppHost projesi yok; yerel stack docker-compose.yml, Grafana/Prometheus, Jaeger ve OpenTelemetry Collector ile yönetiliyor. Aspire bölümünü mevcut kod örneği gibi göstermeyin: laboratuvar olarak bir AppHost eklenirse proje/paket sürümleri .NET 10 ile resmi Aspire dokümanından doğrulanmalı; AppHost resource health, endpoint binding ve container ports tek tek test edilmelidir.

VersioningAspire SDK/paketleri .NET runtime sürümüyle aynı numerik sürüm döngüsüne sahip varsayılmamalıdır. 18 Ekim 2026 itibarıyla resmi Aspire dokümanları bu sayfada kaynaklandırılmıştır; örnek kurulumu yaparken o günkü supported release/CLI gereksinimini doğrulayın.

Bu çözümde gözlemleme hedefleri

Prometheus scrape config OTEL Collector exporter'ını scrape ediyor; Grafana provisioning dashboard/data source bağlantılarını içeriyor; Compose Grafana/Jaeger/Collector/Prometheus'u beraber başlatıyor. Uygulamalar OTLP endpoint'iyle Collector'a telemetry gönderiyor. Bu, yerel eğitim topolojisidir: tek broker, tek DB/telemetry backend ve basit config HA/retention/secret/SLO için production referansı değildir.

Kod yürüyüşü: instrument'tan SLI/SLO panosuna

Metric (ölçüm serisi), SLI (kullanıcı deneyimini sayısallaştıran gösterge), SLO (SLI için hedef) ve error budget (hedef dışına çıkma hakkı) farklı kavramlardır. Repoda Telemetry batch duration/points ve AI/RAG/tool sayaçları tanımlı; bunlar tek başına tanımlanmış müşteri SLO'su değildir.

// ObservabilityNames.cs — uygulamanın gerçek metric instrument'ları
public static readonly Histogram<double> BatchFlushMs =
    TelemetryMeter.CreateHistogram<double>("telemetry.batch_flush_ms");
public static readonly Counter<long> PointsIngested =
    TelemetryMeter.CreateCounter<long>("telemetry.points_ingested");
public static readonly Counter<long> ToolInvocations =
    TelemetryMeter.CreateCounter<long>("ai.tool.calls");

Örneğin “başarılı availability isteği oranı” availability SLI, “30 günde %99.9” SLO olabilir; dashboard numerator/denominator, latency percentile, error classification, scrape interval, burn-rate alert ve traffic denominator'ını açıkça tarif etmelidir. Metric'i hangi code path'in record ettiğini ve `AddMeter` ile export pipeline'a alındığını takip edin. Liveness process'in yaşamasını, readiness trafiği güvenle kabul edebilmesini ölçer; `/health` 200 tek başına dependency readiness değildir.

Bu solution'da .NET Aspire AppHost yok; Compose + OpenTelemetry Collector/Prometheus/Grafana kullanılıyor. [Metric definitions](../src/BuildingBlocks/Shared.Observability/ObservabilityNames.cs), [instrument registration](../src/BuildingBlocks/Shared.Observability/ObservabilityExtensions.cs) ve [compose observability config](../docker-compose.yml) incelenebilir. Aspire local orchestration/diagnostics ergonomisi sağlar; production deployment platformu veya SLO yönetim servisi yerine geçmez.

Üretim kapısıAlert on-call aksiyonu üretmeli, cardinality/time-series budget aşılmamalı ve dashboard sorgusu gerçek metric adlarıyla test edilmelidir. SLO hedefini ekip bağımlılıkları, kullanıcı etkisi ve error-budget politikası olmadan seçmeyin.

Tartışma

Örnek olarak “order submit success within 2 sec” SLI tanımlatın. Valid traffic'i, timeout'u, retry'yi, client cancellation'ı, health check'leri ve business acceptance'i açıkça ayırın. Sonra error budget harcanınca release freeze veya risk review kararı kimde olduğunu tartıştırın.

  • DB fail ise liveness mi readiness mi etkilenmeli; service local cache ile kısmi hizmet veriyorsa karar değişir mi?
  • p99'u ölçen histogram bucket'ı yanlış seçildiyse SLO burn alert ne kadar güvenilirdir?
  • Aspire local modelinde dependency ready görünür ama production secret/role eksik: bu drift'i hangi test bulur?
