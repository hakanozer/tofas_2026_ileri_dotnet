Cache hangi problemi çözer, hangisini çözmez?

Cache latency ve tekrarlanan pahalı hesaplama/DB yükünü azaltır; source of truth değildir. Cache-aside: read cache, miss'te source load, cache set; write sonrası invalidate veya versioned key ile stale data yönetir. TTL stale kalma süresine üst sınır getirir ama invalidation propagation garantisi değildir. Negative cache, hot key, TTL jitter, stale-while-revalidate ve per-key single-flight farklı iş profillerine yarar. Cache hit rate tek başına işlevsellik değildir: stale age, p95, backend miss amplification, memory evictions ve error rate'i de izleyin.

Cache key canonicalization deterministik olmalı, tenant/role/locale/filter/page ve model version gibi sonucu etkileyen bütün boyutları kapsamalıdır. PII veya yetkili içerik için key erişimi/ACL değerlendirin. JSON schema değişince eski entry parse edilemeyebilir; cache değerine version prefix koyun ve migration/eviction planlayın. Cache stampede, TTL bittiğinde binlerce concurrent request'in aynı DB query'sine düşmesidir; distributed lock veya single-flight destek olur ama lock lease expiry ve owner crash davranışını test edin.

Projede iki Redis kullanım profili

CacheAsideBehavior, IDistributedCache ile query response cache'liyor; Medallion distributed lock ile cache miss single-flight deniyor, lock alınamazsa kısa bekleyip fallback load yapıyor. Lock provider hata verince warning ile degrade etmesi availability-first kararıdır; stampede güvenlik ağı garanti olmaktan çıkar, backend load alarmı gerekir. JSON serialization exception'ında entry evict ediliyor.

RedisTenantQuotaStore, gateway replica'ları arasında günlük tenant token usage sayacı tutuyor. Redis'teki INCR atomik olsa da current implementation'daki GET remaining ardından modele çağrı yapıp usage sonradan düşmek eşzamanlı rezervasyon yarışı doğurabilir: birden çok istek aynı kalan bütçeyi görebilir. Ayrıca günlük anahtar reset/TTL ve UTC day window birlikte ele alınmalıdır. Sert maliyet limiti gerekiyorsa atomic reservation/lease (Lua/script veya transaction) ve provider-reported token usage kullanın; tahmini chars/4 sayaç mutabakat değildir.

Invalidation ve cache tutarlılığı

InventoryReservedDomainEvent, tam SKU anahtarı ile pattern invalidation key'leri bildiriyor. Redis Pub/Sub volatile'dır: offline subscriber mesajı kaçırır; pattern scan yüksek key cardinality'de pahalı olabilir. Durable invalidation gerekiyorsa Outbox event'i, versioned cache key veya CDC ile replay edilebilir mekanizma düşünün. Handler'ın publish etmesi ile business transaction arasında dual-write varsa, cache eski kalsa bile update tamamlanmış görünebilir. “Stale kabul edilebilir” kararını domain ve kullanıcı beklentisiyle kayda alın.

Redis down iken davranış workload'a göre seçilir: read cache fail-open DB'ye yük bindirir; fail-closed read availability'yi düşürür; quota store fail-open maliyet limitini aşırabilir. Tek policy her key'e uymaz. Redis memory max, eviction policy, persistence/replication, TLS/auth, backup/restore ve multi-AZ failover ayrı operasyonel konulardır.

Doğrulama planı

  • Cache hit/miss ve source query sayısını karşılaştırın; query latency değil uçtan uca latency ölçün.
  • 100+ concurrent miss ile stampede, lock timeout ve fallback path'i doğrulayın.
  • Redis'i durdurup cache, lock ve quota policy'lerinin birbirinden farklı çalıştığını gözleyin.
  • Tenant/role/locale varyasyonlarında key collision veya veri sızıntısı testi yapın.
  • Eviction, failover ve stale entry senaryolarında freshness SLO'sunu ölçün.

Kod yürüyüşü: cache-aside ve kota kontrolünün farkı

Bu repoda iki Redis kullanımını karşılaştırın: CQRS query pipeline'ındaki cache-aside (önce cache oku, miss'te kaynağa git) ve AI gateway'in token budget sayaçları. Biri kısa TTL'li read optimization, diğeri maliyet/kullanım kontrolü; failure policy'leri aynı seçilmemelidir.

// Query cache: key + 30 saniyelik freshness penceresi
public string CacheKey => $"inventory:availability:{Sku}";
public TimeSpan? AbsoluteExpiration => TimeSpan.FromSeconds(30);

// LLM quota middleware: check-before-use ve response stream sayacı
var tenant = context.Request.Headers[TenantHeader].FirstOrDefault()
    ?? context.User.FindFirst("tenant_id")?.Value;
if (string.IsNullOrWhiteSpace(tenant))
{
    context.Response.StatusCode = StatusCodes.Status400BadRequest;
    return;
}
var remaining = await quotas.GetRemainingAsync(tenant, context.RequestAborted);
if (remaining <= 0)
{
    context.Response.StatusCode = StatusCodes.Status429TooManyRequests;
    return;
}
var originalBody = context.Response.Body;
var counter = new TokenCountStream(originalBody);
context.Response.Body = counter;
try
{
    await next(context);
}
finally
{
    context.Response.Body = originalBody;
    await quotas.RecordUsageAsync(tenant, counter.TokensWritten, context.RequestAborted);
}

Query cache miss'te distributed lock tek-yükleme mekanizması sağlar; lock alınamazsa davranışın DB'ye kaç eşzamanlı fallback üreteceği yük testinde ölçülmeli. Invalidation yalnız local memory'den değil, tüm replika/cache katmanlarından tutarlı biçimde ele alınmalıdır. Cache key tenant/authorization kapsamını içermeli ise mevcut Inventory demo query'deki SKU-only key'i production öncesi genişletin.

Quota örneğinde read-check ile sonradan INCR arasında yarış vardır: eşzamanlı çağrılar aynı kalan miktarı okuyup bütçeyi aşabilir; usage tahmini de chars/4 olup provider billing usage değildir. [Cache behavior](../src/BuildingBlocks/Shared.Kernel/Caching/CacheAsideBehavior.cs), [query contract](../src/Services/Inventory/Inventory.Application/Queries/GetInventoryAvailabilityQuery.cs) ve [AI quota middleware/store](../src/Gateway/ApiGateway/Middleware/LlmTokenBudgetMiddleware.cs) açılıp farkları gösterin.

İki ayrı availability kararıRead cache Redis'ten geçici olarak vazgeçip origin'e gidebilir; kota Redis'i fail-open davranırsa maliyet limiti bypass olur. Üretim quota'sında tek atomik reserve/check (ör. Lua script veya transaction), idempotent usage record, provider gerçek token usage mutabakatı, key TTL ve alarm gerekir.

Tartışma

İki replika üzerinde local memory quota ile Redis quota'yı karşılaştırın. Sonra aynı anda iki isteğin “kalan son token”ı almasına izin verip atomic reservation tasarımını katılımcılara düşündürün. Cache'in hangi durumda yalnızca hızlandırıcı, hangi durumda iş doğruluğu bileşeni olduğunu netleştirin.

  • Cache write fail olunca DB okuması başarılıysa kullanıcıya 503 dönmek doğru mu?
  • Invalidation event'i kaçıran replica'da stale veri ne kadar süre kabul edilebilir?
  • Redis key'e tenant claim eklemek yeterli mi; tenant ID'nin kaynağına ne kadar güveniyorsunuz?
