Redis ve caching stratejileri

Redis bu projede üç ayrı iş yapar: oturum (JWT) kaydı, okuma hızlandırıcı cache ve paylaşılan sayaç. Her biri farklı TTL, anahtar ve hata politikası ister; cache hit oranını tek başına başarı ölçüsü saymayın.

  2. Gateway: login'de JWT oturumunun Redis'e yazılması, her istekte doğrulanması, logout'ta silinmesi

Redis projede ne için kullanılıyor?

Tek bir Redis örneği (redis:8.10.2-alpine) dört farklı sorumluluğa hizmet eder. Hepsinde Redis source of truth değildir (oturum kaydı hariç, bkz. aşağıda): kaybolursa veri PostgreSQL'den yeniden üretilebilir. Oturum kaydı ise “bu token hâlâ geçerli mi?” sorusunun cevabıdır; bu yüzden hata politikası farklıdır.

Cache hangi problemi çözer, hangisini çözmez?

Cache latency ve tekrarlanan pahalı hesaplama/DB yükünü azaltır. Cache-aside akışı: önce cache'i oku; miss ise kaynaktan yükle ve cache'e yaz; yazma işleminden sonra ilgili anahtarı sil (invalidate) veya versiyonlu anahtar kullan. TTL stale kalma süresine üst sınır koyar ama invalidation'ın ulaştığını garanti etmez; invalidation başarısız olsa bile veri en fazla TTL kadar bayat kalır.

İstek → Redis GET → hit: dön · miss: PostgreSQL → Redis SET (TTL) → dön

Cache key; sonucu etkileyen tüm boyutları (kullanıcı/tenant, rol, dil, filtre, sayfa, model versiyonu) kapsamalıdır. PII veya yetkili içerik için anahtar erişimini ayrıca değerlendirin. JSON şeması değişirse eski kayıt parse edilemeyebilir: bu durumda kaydı sil ve kaynağa düş (projede JsonException yakalanıp miss sayılır). Cache stampede, TTL bittiğinde binlerce eşzamanlı isteğin aynı DB sorgusuna düşmesidir; distributed lock veya single-flight yardımcı olur, ancak lock lease süresi ve owner crash davranışı test edilmelidir. Hit rate'in yanında stale age, p95, miss amplification, eviction ve hata oranını da izleyin.

Gateway: JWT oturumu Redis'te zamana bağlı tutulur

POST /api/auth/login başarılı olunca gateway bir JWT üretir ve bu JWT'nin benzersiz kimliğini (jti claim'i) Redis'e yazar. İmza ve süre kontrolü tek başına yetmez: token çalınsa veya kullanıcı çıkış yapsa bile JWT kendi süresi dolana kadar kriptografik olarak geçerli kalır. Redis kaydı bu boşluğu kapatır: anahtar yoksa token reddedilir.

login → JWT(jti) üret → SET auth:session:{jti} (TTL = token ömrü) → cookie
her istek → imza + süre doğrula → EXISTS auth:session:{jti} → yoksa 401
logout → DEL auth:session:{jti} → eski token artık 401
OlayRedis işlemiSonuç
Login başarılıSET auth:session:{jti} {userId} EX 36000Oturum başladı; TTL token exp süresiyle aynı
Korumalı istekEXISTS auth:session:{jti}Var → devam; yok → 401
TTL dolduRedis anahtarı kendiliğinden silerJWT exp ile aynı anda geçersiz; temizlik işi gerekmez
LogoutDEL auth:session:{jti}Cookie silinmese/sızsa bile token anında geçersiz

Kod üç yerde değişir: JwtTokenService token'a jti ekler; ITokenSessionStore / RedisTokenSessionStore Redis erişimini soyutlar; AuthEndpoints login'de kaydı yazar, logout'ta siler; AuthServiceExtensions içindeki OnTokenValidated olayı her istekte kaydı kontrol eder.

// TokenSessionStore.cs — anahtar jti, TTL token ömrü kadar
public static string Key(string jti) => $"auth:session:{jti}";

public Task StoreAsync(string jti, Guid userId, TimeSpan ttl, CancellationToken ct = default)
    => redis.GetDatabase().StringSetAsync(Key(jti), userId.ToString(), ttl);

public Task<bool> IsActiveAsync(string jti, CancellationToken ct = default)
    => redis.GetDatabase().KeyExistsAsync(Key(jti));

// AuthEndpoints.LoginAsync — cookie'den ÖNCE Redis'e yazılır
var issued = tokens.Issue(user);
await sessions.StoreAsync(issued.Jti, user.Id, issued.ExpiresAt - DateTimeOffset.UtcNow, ct);

// AuthServiceExtensions — imza geçerli olsa bile oturum kaydı şart
OnTokenValidated = async ctx =>
{
    var jti = ctx.Principal?.FindFirst("jti")?.Value;
    if (string.IsNullOrEmpty(jti) || !await store.IsActiveAsync(jti, ct))
        ctx.Fail("Session is not active.");
}
Oturum kaydı için fail-closedRedis'e ulaşılamazsa gateway token'ı kabul etmez (401) ve login 503 döner. Burada fail-open seçmek, Redis kesintisinde logout'u ve iptal edilmiş token'ları bypass ederdi. Bu bilinçli bir güvenlik/erişilebilirlik takasıdır; Redis'in yüksek erişilebilirliği (replica/failover) bu yüzden önemlidir.
Kapsam sınırıOturum kontrolü gateway'dedir. Order/Inventory servisleri JWT'yi kendi imza anahtarıyla bağımsız doğrular ve Redis'e bakmaz; yani gateway'i atlayıp servise doğrudan giden bir istek, logout sonrası da token süresi dolana kadar kabul edilebilir. Servislerin ağdan yalnızca gateway'e açık olması bu varsayımın parçasıdır. Servis tarafında da iptal gerekiyorsa aynı ITokenSessionStore mantığı oraya taşınmalıdır.
Eviction ve oturum kaybıdocker-compose.yml Redis'i --maxmemory 512mb --maxmemory-policy allkeys-lru ile başlatır. Bellek dolarsa allkeys-lru oturum anahtarlarını da silebilir ve kullanıcılar beklenmedik şekilde çıkış yapmış olur. Eğitimde sorun olmaz; üretimde oturumları ayrı bir Redis'e alın veya yalnızca TTL'li anahtarları silen volatile-lru kullanın ve memory/eviction alarmı kurun.

Order servisi: liste cache'i ve create'te invalidation

Sipariş listesi sık okunur, nadiren değişir; bu yüzden OrderService cache-aside uygular. Cache arayüzü IOrderListCache (Redis uygulaması RedisOrderListCache) üç işlem sunar: GetAsync, SetAsync, InvalidateAsync. Anahtar kullanıcı bazlıdır: orders:user:{userId}:list; userId daima JWT'den gelir, istek gövdesinden değil.

EndpointRedis davranışı
GET /orders (ListAsync)Önce GET. Hit ise Redis'teki liste döner, DB'ye gidilmez. Miss ise DB'den son 100 sipariş okunur, SET ... EX 60 ile cache'e yazılır.
POST /orders (CreateAsync)Sipariş kaydedilince DEL orders:user:{userId}:list. Durum değişimi (Confirmed/Rejected) kaydedildikten sonra finally bloğunda bir kez daha silinir.
GET /orders/{id} (GetAsync)Cache kullanmaz; userId filtresiyle doğrudan DB'den okur.
// OrderService.ListAsync — cache-aside
var cached = await cache.GetAsync(userId, ct);
if (cached is not null) return cached;               // HIT

var orders = await db.Orders.AsNoTracking().Include(o => o.Items)
    .Where(o => o.UserId == userId)
    .OrderByDescending(o => o.CreatedAt).Take(MaxListSize).ToListAsync(ct);
var dtos = orders.Select(OrderDto.From).ToList();
await cache.SetAsync(userId, dtos, ct);              // MISS → SET + TTL
return dtos;

// OrderService.CreateAsync — yazma sonrası invalidate
db.Orders.Add(order);
await db.SaveChangesAsync(ct);
await cache.InvalidateAsync(userId, ct);             // Pending kaydı görünsün
...
finally { await cache.InvalidateAsync(userId, CancellationToken.None); }  // nihai durum
Neden iki kez invalidate?Sipariş önce Pending olarak yazılır, sonra Inventory cevabıyla Confirmed/Rejected olur. İlk silme ile ikinci kayıt arasında başka bir GET /orders listeyi Pending hâliyle cache'e yazmış olabilir; son silme bu eski görüntüyü temizler. İptal edilmiş istekte bile silinsin diye CancellationToken.None kullanılır.

Cache hatası isteği düşürmemelidir: RedisOrderListCache Redis veya JSON hatasını loglar, Get için null (miss) döner, Set/Invalidate hatasını yutar. Invalidate başarısız olursa bayat liste en fazla OrderListTtlSeconds (60 sn) yaşar; bu üst sınır TTL'in asıl işidir. TTL'i appsettings içindeki Cache:OrderListTtlSeconds ile değiştirebilirsiniz.

Ortak cache davranışı ve kota sayacı

CacheAsideBehavior, IDistributedCache ile CQRS query response'larını cache'ler; Medallion distributed lock ile miss anında tek-yükleme (single-flight) dener, lock alınamazsa kısa bekleyip fallback yükleme yapar. Lock provider hata verirse warning ile degrade etmesi availability-first bir karardır; stampede güvenlik ağı garanti olmaktan çıkar, bu yüzden backend yük alarmı gerekir. JSON serialization hatasında kayıt evict edilir.

RedisTenantQuotaStore, gateway replikaları arasında günlük tenant token kullanımını sayar. Redis INCR atomiktir; ancak “önce GET remaining, sonra modele çağrı, kullanımı sonradan düş” akışı eşzamanlı rezervasyon yarışı doğurur: birden çok istek aynı kalan bütçeyi görebilir. Sert maliyet limiti için atomic reservation (Lua script/transaction) ve sağlayıcının bildirdiği gerçek token kullanımı gerekir; chars/4 tahmini mutabakat değildir.

Invalidation ve cache tutarlılığı

İki invalidation yaklaşımı vardır. Order servisi doğrudan silme kullanır: yazan kod aynı serviste olduğu için sade ve güvenilirdir. Inventory ise InventoryReservedDomainEvent ile tam SKU anahtarı ve pattern anahtarlarını bildirir. Redis Pub/Sub volatile'dır: çevrimdışı subscriber mesajı kaçırır; pattern scan yüksek key cardinality'de pahalıdır. Kalıcı invalidation gerekiyorsa Outbox event'i, versiyonlu anahtar veya CDC ile tekrar oynatılabilir bir mekanizma düşünün.

DB yazması ile cache silme iki ayrı işlemdir (dual-write): silme başarısız olursa veri güncel ama cache eski kalır. “Stale kabul edilebilir” kararını ve süresini (TTL) domain ve kullanıcı beklentisiyle yazılı hâle getirin.

Redis erişilemezse: üç farklı politika

Tek bir hata politikası her anahtara uymaz. Karar, “bu veri doğruluğu mu hızı mı temsil ediyor?” sorusundan çıkar.

KullanımPolitikaGerekçe
Sipariş listesi cache'iFail-openCache yalnız hızlandırıcıdır; DB'ye düşmek doğru sonuç verir (yük artar).
JWT oturum kaydıFail-closedKayıt güvenlik kararıdır; doğrulanamayan oturum kabul edilmez.
LLM kotasıMaliyete göre seçilirFail-open limiti aşırabilir; fail-closed AI'ı durdurur.

Redis memory max, eviction policy, persistence (AOF), replication, TLS/auth, backup/restore ve multi-AZ failover ayrı operasyon konularıdır. Yerel ortamda appendonly yes ve allkeys-lru ayarları docker-compose.yml içindedir.

Güvenlik ve gözlemleme

  • Anahtar kapsamı: kullanıcıya özel cache anahtarı userId içerir; cache'ten dönen veri başka kullanıcıya sızamaz.
  • Oturum anahtarı: jti tahmin edilemez (Guid) ve değer olarak yalnız userId saklanır; token'ın kendisi Redis'e yazılmaz.
  • Veri minimizasyonu: cache'e PII ve gizli bilgi yazmayın; yazıyorsanız kısa TTL ve erişim kontrolü uygulayın.
  • İzleme: hit/miss, Redis hata logları, evicted_keys, bellek kullanımı, login/logout oranı ve 401 artışı.

Doğrulama planı (redis-cli ile)

Aşağıdaki komutlar compose'taki Redis konteynerinde çalışır: docker exec -it elp-redis redis-cli.

  1. Login: POST /api/auth/login sonrası --scan --pattern 'auth:session:*' bir anahtar göstermeli; TTL auth:session:<jti> yaklaşık 36000 saniye (600 dk) olmalı.
  2. Doğrulama: aynı cookie ile GET /api/auth/me 200 dönmeli.
  3. Logout: POST /api/auth/logout sonrası EXISTS auth:session:<jti> 0 olmalı; aynı token ile /api/auth/me artık 401 dönmeli.
  4. Liste cache'i: GET /api/orders iki kez çağrılınca orders:user:<userId>:list oluşmalı (TTL ≤ 60); ikinci çağrı DB'ye gitmemeli (Debug log: cache hit/miss).
  5. Invalidation: POST /api/orders sonrası EXISTS orders:user:<userId>:list 0 olmalı; sonraki GET yeni siparişi içermeli.
  6. Redis kesintisi: docker stop elp-redis ile sipariş listesi hâlâ cevap vermeli (fail-open), korumalı gateway istekleri ise 401 dönmeli (fail-closed).
  7. Kullanıcı izolasyonu: iki kullanıcıyla liste çağırın; anahtarlar ayrı olmalı, veri karışmamalı.

Kod yürüyüşü: aynı Redis, üç farklı sözleşme

Sırayla şu dosyaları açıp farkı gösterin: TokenSessionStore (güvenlik kaydı, fail-closed), OrderListCache (okuma hızlandırıcı, fail-open) ve LlmTokenBudgetMiddleware (sayaç, maliyet kontrolü). Üçü de IConnectionMultiplexer kullanır; fark Redis çağrısında değil, hata yakalamada ve TTL seçimindedir.

// Fail-open (OrderListCache): hata → miss, istek devam eder
catch (Exception ex) when (ex is RedisException or JsonException)
{
    logger.LogWarning(ex, "Order list cache read failed for user {UserId}", userId);
    return null;
}

// Fail-closed (AuthServiceExtensions): hata → token reddedilir
catch (RedisException ex)
{
    logger.LogError(ex, "Redis session check failed; rejecting token.");
    ctx.Fail("Session store unavailable.");
}

// Query cache: key + 30 saniyelik freshness penceresi
public string CacheKey => $"inventory:availability:{Sku}";
public TimeSpan? AbsoluteExpiration => TimeSpan.FromSeconds(30);

Query cache anahtarı yalnız SKU içerir; veri kullanıcıya özel değilse sorun değildir, ancak yetkiye göre değişen bir sonuç için production öncesi tenant/rol boyutu eklenmelidir. Kota akışında read-check ile sonradan INCR arasındaki yarışı da ayrıca gösterin.

Üç ayrı availability kararıRead cache Redis'ten geçici olarak vazgeçip origin'e gidebilir; oturum kaydı vazgeçemez; kota Redis'i fail-open davranırsa maliyet limiti bypass olur. “Redis down” tek bir senaryo değil, her kullanım için ayrı tasarlanmış bir davranıştır.

Tartışma

Redis'i docker stop elp-redis ile durdurup üç davranışı canlı gözlemleyin: sipariş listesi çalışmaya devam eder, korumalı gateway istekleri 401 döner, kota davranışı koda göre değişir. Sonra “cache ne zaman yalnız hızlandırıcıdır, ne zaman doğruluk/güvenlik bileşenidir?” sorusunu katılımcılara tartıştırın.

  • Oturum kaydı için fail-open seçilseydi logout ve iptal ne anlama gelirdi?
  • Order servisi de oturum kaydını kontrol etmeli mi; bunun maliyeti ve kazancı nedir?
  • İlk invalidate ile ikinci invalidate arasındaki yarışta liste ne kadar süre bayat kalabilir?
  • allkeys-lru bellek baskısında kullanıcıları neden çıkış yapmış gibi gösterebilir?
  • Cache yazma başarısız olunca DB okuması başarılıysa kullanıcıya 503 dönmek doğru mu?
