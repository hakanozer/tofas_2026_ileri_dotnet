Profiling: darboğazı bulmadan çözüm seçmeyin

CPU profiler hot path ve call tree'yi; allocation profiler allocation stack ve retained heap'i; trace/metrics runtime GC, thread pool, lock, network/DB latency'yi gösterir. Production benzeri workload, release build, runtime/CPU/container limit'i ve warm-up koşulları kaydedilmelidir. CPU-bound ile I/O-bound yükü ayırın. Flame graph'ta yüksek toplam süre çağrı sayısından, yüksek self-time fonksiyonun kendi maliyetinden gelebilir. Bir CPU optimize ederken lock contention veya DB connection pool darboğazını büyütebilirsiniz.

Observability instrumentation'ın overhead'i ölçüm ortamında da bulunmalıdır. Sampling oranı, exporter queue ve log level sonuçları değiştirebilir. Baseline ve varyant aynı veri hacmi, aynı hardware, aynı concurrency ve aynı dependency durumunda kıyaslanmalıdır. Ortalama latency tail'i gizler; p50/p95/p99, throughput ve error rate'i birlikte raporlayın.

BenchmarkDotNet: microbenchmark neyi kanıtlamaz?

BenchmarkDotNet JIT warmup, iteration, process isolation ve istatistik yardımıyla CPU/memory microbenchmark'ı üretir; parser, serializer, allocator veya tek algorithm karşılaştırmasında uygundur. Benchmark gerçek web service concurrency'sini, network, TLS, DB, message broker, queueing ve autoscaling davranışını tek başına temsil etmez. Basit testte dead-code elimination, constant folding, unrealistic input ve Tiered JIT/PGO etkisini değerlendirin. `MemoryDiagnoser` allocation farkını gösterir ama üretim GC/latency'nin tamamı değildir.

// Bir benchmark projesinde ölçülen saf işlev olmalı; BDN package
// uygulama projesinden ayrı, sabit test input'larıyla çalıştırılır.
[MemoryDiagnoser]
public class ParserBenchmarks
{
    private readonly byte[] _payload = CreateRepresentativePayload();

    [Benchmark]
    public TelemetryPayload Parse() =>
        TelemetryPayload.DeserializeFromUtf8(_payload);
}

Yukarıdaki parça çalışma bağlamı gösterir; CreateRepresentativePayload ve modelin projede erişilebilirliğine göre benchmark project'i tamamlanmalıdır. Repo'da BenchmarkDotNet projesi yoktur; paketi ekleyip restore/build/benchmark run yapılmadığı için bu örnek repository içinde doğrulanmış benchmark değildir.

Yük testinin türünü ve kapasite sorusunu seçin

Test türüSorduğu soruÖrnek ölçüm
Load / capacityHedef trafik profili içinde SLO korunuyor mu?RPS, p95/p99, error budget, resource utilization
StressKırılma noktası ve graceful degradation nerede?Queue age, 429/503, pool saturation, recovery
SpikeAni burst ve scale-up gecikmesinde sistem ne yapar?Cold start, backlog, cache stampede, autoscale
SoakSaatler/günler içinde leak veya gradual degradation var mı?Heap/handles, connection leak, queue growth, token cost

Closed-loop virtual users, server yavaşlayınca daha az request üreterek coordinated omission yapabilir; açık modelde hedef arrival rate sabit tutulur. Test client'ının CPU/network kapasitesi de darboğaz olabilir. Test verisi dağılımı, cache warm/cold oranı, tenant skew ve message payload üretimdeki profile uymalıdır.

Güvenli test planı

  1. Ölçülebilir hipotez yazın: “Channel capacity 1k'dan 4k'ya çıkınca throughput artar mı; memory ve p99 ne olur?”
  2. Known-good baseline ve sabit deployment/data seed alın.
  3. Hedefi test owner ve dependency owner'larıyla sınırlı staging/canary ortamına yönlendirin.
  4. Traffic, errors, latency, CPU/GC, DB pool, Kafka lag/queue age ve downstream quota izleyin.
  5. Stop condition, data cleanup, test tenant, rate limit ve rollback hazır olsun; gerçek kullanıcı/veri ya da prod endpoint'e izinsiz yük göndermeyin.
  6. Raw output, commit, SDK/runtime, container resource limit ve tool version ile sonuçları tekrarlanabilir kaydedin.

Kod yürüyüşü: benchmark'tan yük testine geçerken soruyu değiştirin

Repoda BenchmarkDotNet veya k6/Locust projesi bulunmuyor; buna karşılık Kafka consumer batch duration, channel backlog, deserialize errors ve throughput counter'ları var. Önce real service'te baseline alın, sonra profiling ile allocation/CPU hotspot belirleyin. Microbenchmark bir fonksiyonun izole maliyetini ölçer; broker, DB, network, contention veya production capacity kanıtlamaz.

// KafkaTelemetryConsumer.FlushBatchAsync — gerçek flush/commit ölçümü
var sw = Stopwatch.StartNew();
var pooledBatch = new PooledTelemetryBatch(
    [.. batch], rentedBuffers.ToArray(), _pool);
await _channel.Writer.WriteAsync(pooledBatch, ct);
_consumer.StoreOffset(lastResult);
_consumer.Commit();
BatchProcessDuration.Record(sw.Elapsed.TotalMilliseconds);

Yük testi hipotezi örneği: “worker concurrency 4'ten 8'e çıkınca p95 ingest latency düşecek, DB CPU ve Kafka lag SLO sınırını aşmayacak.” Sabit seed/data volume, warmup, ramp/steady/cooldown, run duration, error rate, saturation signals, host/container version, CPU/memory limit ve percentile capture tanımlayın. Stress test kapasite sınırını, soak test leak/queue drift'i, spike test ani artış tepkisini arar.

BenchmarkDotNet'i isolated helper/serialization path için ayrı test project'e ekleyin; paket/runner repoda yok ve sample komutu doğrulanmış repo workflow'u değildir. [Kafka counters](../src/Services/Telemetry/TelemetryStreamProcessor/Kafka/KafkaTelemetryConsumer.cs), [batch Activity](../src/Services/Telemetry/TelemetryStreamProcessor/Processing/TelemetryBatchProcessor.cs), [runtime/HTTP metrics](../src/BuildingBlocks/Shared.Observability/ObservabilityExtensions.cs) aynı raporda korele edilmelidir.

Performance claim formatı“Daha hızlı” yerine workload, payload distribution, concurrency, environment, warmup, p50/p95/p99, allocations/op, CPU, GC, error rate ve confidence/variance rapor edin. İyileştirme throughput'u artırıp tail latency veya cloud cost'u kötüleştirmiş olabilir.

Tartışma

Kafka telemetry batch size değişikliğini örnek hipotez yapın. Microbenchmark'ta parse throughput, load test'te DB bulk write throughput, soak test'te buffer return/GC davranışı farklı deneylerdir; birini diğerine kanıt gibi sunmayın.

  • RPS yükselirken p99 da hızla artıyorsa sistemin ilk saturation sinyali nedir?
  • Benchmark 20% hızlandı ama production latency değişmedi: hangi bağımlılık ve workload etkilerini araştırırsınız?
  • Hangi aşamada test durdurulur ve testin kendi maliyet/yan etkisi nasıl kontrol edilir?
