Bağımlılık yönü neden önemlidir?

Katmanlı mimaride sunum, uygulama/use-case, domain ve altyapı sorumlulukları ayrılır. Temiz/hexagonal mimaride iç politika (domain ve application) dış teknoloji ayrıntılarını bilmez; database, HTTP, broker ve filesystem adapter'ları iç sözleşmeleri uygular. Dış katmanların iç katmana compile-time referansı bulunması doğaldır; ters yönde, domain'in EF Core/Npgsql veya ASP.NET'e bağımlı olması kuralın ihlalidir. Dependency inversion, DI container kullanmaktan ibaret değildir: kaynak kod bağımlılık yönünü port/interface belirler.

HTTP endpoint'in görevi request doğrulama/kimlik ve response mapping; application use-case'i orkestrasyon; domain'i invariant ve state transition; infrastructure'ı kalıcılık ve dış sistem erişimidir. Her işi repository üstüne yığmak, anemic domain ve devasa service sınıfları üretir. Öte yandan her property için interface/handler/factory tanımlamak da değişim noktası olmayan soyutlama vergisidir.

Bu çözümdeki gerçek katmanlar

Order ve Inventory projeleri Domain/Application/Infrastructure/API olarak ayrılmış. Shared.Kernel, Shared.Grpc ve Shared.Observability ortak yapı taşları; ancak paylaşılan kernel'e domain'e özgü bütün modelleri koymak context sınırlarını eritir. Composition root, API/worker Program.cs içinde adapter'ları DI'a kaydeder. Mevcut Order API'de application/domain kullanımı yok denecek kadar az; proje klasörlerinin bulunması use-case'in tamamlandığını kanıtlamaz.

// İncelenecek bağımlılık grafiği (temsili, repo proje ayrımıyla uyumlu)
Order.Api
  ├── Order.Application
  └── Shared.Observability
Order.Application
  └── Order.Domain
Order.Infrastructure
  └── Order.Application (port implement eder)

Grafiği gerçek .csproj ProjectReference satırlarıyla doğrulayın. Domain'in persistence annotation'ı kullanıp kullanmadığını da tarayın. Kodun derlenmesi katman sınırlarının doğru uygulandığı anlamına gelmez.

Use-case'i dikey dilim olarak tasarlayın

Örneğin “stok ayır” use-case'inde API bir application command çağırır; application policy gereği Inventory port'undan aggregate yükler; aggregate miktar invariant'ını uygular; unit of work değişikliği saklar; domain event'i aynı transaction/outbox sınırında entegrasyon mesajına dönüştürülür. Port'un implementasyonu EF/Npgsql kullanabilir. Uygulama katmanındaki port, use-case'in ihtiyaç duyduğu davranışı tanımlar; genel amaçlı CRUD repository'ye dönüşmemelidir.

Güvenli transaction sınırıEF Core transaction'ı ile broker publish'i tek atomik transaction değildir. Application handler içinde SaveChangesAsync() ardından doğrudan publish yapılması dual-write aralığı bırakır; 08. oturumdaki Outbox çözümüne geçin.

Test stratejisinde saf domain testleri invariant'ları, application testleri use-case orkestrasyonunu fake portlarla, adapter integration testleri gerçek veritabanı/broker davranışını sınar. SQLite in-memory veya mock DbSet, PostgreSQL kilit/SQL/transaction davranışını taklit etmez.

Kod yürüyüşü: composition root'tan gerçek use-case'e

Katmanlı mimarinin değerini klasör adları değil, derleme bağımlılığı ve istek akışının gerçekten hangi katmanlara girdiği gösterir. Bu repoda API/Application/Domain/Infrastructure projeleri ayrılmış olsa da Order API henüz use-case çalıştırmıyor. Önce gerçek API host'unu okuyun; sonra proje referanslarını solution'daki .csproj dosyalarında doğrulayın.

// Order.Api/Program.cs — mevcut uygulama yüzeyi
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/health", () => Results.Ok(new { status = "healthy", context = "orders" }));
app.MapGet("/", () => Results.Ok(new { message = "Order service — Day 1 ES/CQRS labs land here" }));
app.Run();

Bu kesit HTTP → application command → domain aggregate → persistence adapter zincirini göstermiyor; dolayısıyla sahnede “dört proje var, clean architecture tamam” demeyin. [Order API Program.cs](../src/Services/Order/Order.Api/Program.cs) ile [Order project dosyalarını](../src/Services/Order/) yan yana açın: composition root, dış adapter kayıtlarının doğal yeridir. Uygulanmış olmayan bir use-case'i varmış gibi örneklemeyin.

Beklenen dikey dilim (tek iş davranışını uçtan uca taşıyan değişiklik): HTTP DTO → Application command/handler → domain davranışı/invariant → port arayüzü → Infrastructure implementasyonu → response. Domain testinde DB mock'lamayın; invariant'ı saf test edin. Adapter testi için gerçek PostgreSQL sağlayıcısını ve transaction davranışını sınayın.

Sınıfta gösterilecek mimari riskiInfrastructure doğrudan Domain'e bağlanıp EF/Npgsql tiplerini domain modeline sızdırırsa iç politika dış teknolojiye kilitlenir. Tersine, küçük bir endpoint için her katmana gereksiz interface/factory eklemek değişim noktası olmayan soyutlama vergisi üretir.

Tartışma

Solution Explorer'da katmanları açın; ardından API'den domain'e kadar tek endpoint'i takip edin. İz süremiyorsanız mimariyi çizimden değil, mevcut bağlantılardan anlatın. Domain projesinin boş sınıfını da açıkça gösterip “hedef topoloji ile teslim edilmiş davranış” farkını belirginleştirin.

  • Bir use-case için repository port'u Domain'de mi Application'da mı tanımlanmalı? Kriteriniz değişim nedeni ve tüketici ihtiyacı olsun.
  • Test kolaylığı için interface eklemek ne zaman yararlı, ne zaman gereksiz?
  • Infrastructure'ı ayrı assembly yapmak deploy/runtime izolasyonu sağlar mı, yalnızca compile-time izolasyonu mu?
