DDD, domain event ve Event Sourcing

Domain modelini gerçek iş invariant'larının diliyle kurun; Event Sourcing'i ise yalnızca geçmişi saklamak gerçekten ürün gereksinimiyse tercih edin.

DDD'nin çözmeye çalıştığı problem

Domain-Driven Design, karmaşık iş politikasını teknik modelin merkezine koyar. Ubiquitous language, domain uzmanı ve geliştiricinin aynı terimi aynı anlamda kullanmasını sağlar; bounded context ise aynı kelimenin farklı context'teki anlamlarını sınırlı tutar. Aggregate, bir transaction içinde korunması gereken invariant'ların tutarlılık sınırıdır. Aggregate root dışarıya kontrollü operasyon sunar; başka aggregate'ların iç koleksiyonlarını doğrudan güncellemek invariant'ı atlatır.

Entity kimlikle süreklidir; value object değeriyle eşitlenir ve mümkün olduğunda immutable tutulur. Domain event, domain içinde gerçekleşmiş bir olguyu ifade eder; integration event ise servis sınırını geçen, sürümlü ve taşınabilir sözleşmedir. Domain event'i doğrudan broker payload'ı yapmak domain modelini dış sözleşmeye bağlar. Mapping ve Outbox, sınırı yönetilebilir kılar.

Repo örneğiInventoryReservedDomainEvent cache invalidation niyetini taşıyor; ama bu dosya tek başına bir aggregate, persistence transaction'ı veya durable event dispatch mekanizması kanıtlamaz. Order.Domain içindeki boş Class1, DDD modelinin henüz örneklenmediğini gösterir.

Event Sourcing: event kaydı sistemin kaynağıdır

Klasik state persistence son durum satırını yazar; Event Sourcing ise aggregate için iş olaylarının append-only dizisini otoritatif kayıt yapar. Aggregate olayları sırayla replay ederek state'i yeniden kurar; read model projection'ları asenkron güncellenebilir. Bu, denetim izi, temporal sorgu ve geçmişten yeni projection üretme sağlar. Bedeli: event schema evolution, replay süresi, snapshot, projection lag, duplicate delivery, silme/KVKK talepleri ve operasyonel arşiv yönetimi.

// Kavramsal event sözleşmesi; çalışan repo implementasyonu değildir.
public sealed record InventoryReserved(
    Guid ReservationId, string Sku, int Quantity,
    long AggregateVersion, DateTimeOffset OccurredAt);

// Expected version kontrolü: aynı aggregate'e eşzamanlı yazan iki komuttan
// yalnızca biri beklenen version ile append edebilmelidir.
await eventStore.AppendAsync(
    streamId, expectedVersion, events, cancellationToken);

Event store API'si concurrency token/expected revision ile optimistic concurrency uygular. Event'lere PII yazmak silme ve saklama politikasını zorlaştırır; event'e sır ekleyip sonradan log, trace, analytics ve backup'ta unutmak yaygın risk. Event store'u “Kafka'yı açıp event publish etmek” ile eş tutmayın: broker genellikle replayable application state'in authoritative per-aggregate store'u değildir.

Event Sourcing ile event-driven architecture aynı kavram değildir. Son durum tablosundan Outbox ile event yayınlayan servis event-driven olabilir ama Event Sourcing kullanmıyor olabilir.

Kod yürüyüşü: domain olgusu ile servis sözleşmesini ayırın

Repodaki somut örnek OrderPlacedEvent, servisler arasında taşınmak üzere tanımlanmış integration event'tir (servis sınırını aşan, sürümlenebilir iş bildirimi). Bu, tek başına Event Sourcing değildir; Order aggregate'i ve kalıcı event store bu repoda uygulanmış değildir.

// Orchestrator/Contracts/IntegrationEvents.cs içindeki gerçek contract kesiti
public sealed record OrderPlacedEvent
{
    public required Guid OrderId { get; init; }
    public required string Sku { get; init; }
    public required int Quantity { get; init; }
    public required Guid CorrelationId { get; init; }
    public required DateTimeOffset OccurredAt { get; init; }
}

Domain event aynı bounded context içindeki domain davranışının sonucudur; integration event ise tüketicilerden bağımsız, uyumluluk kuralları olan dış contract'tır. Contract'ı değiştirmek eski consumer'ı bozabilir: yeni alanları geriye dönük uyumlu ekleyin, enum/meaning değişimini version edin ve correlation/tenant/PII politikasını belirleyin. [Gerçek event sözleşmeleri](../src/Services/Orchestrator/BackgroundOrchestrator/Contracts/IntegrationEvents.cs) ile [Saga tüketimini](../src/Services/Orchestrator/BackgroundOrchestrator/Sagas/OrderFulfillmentSaga.cs) açın.

Event Sourcing'de ise append-only event stream (yalnızca sona eklenen olay kaydı) authoritative state olur; reducer/projection olayları sırayla uygulayarak güncel görünümü üretir. Bu yaklaşım geçmişi ve “neden bu state'e geldik?” sorusunu yanıtlar, fakat schema evolution, replay, snapshot, concurrency revision, PII silme ve projection rebuild maliyeti getirir. Bu depodaki event stream ve replay'i temsili anlatım olarak ayırın.

// Eğitim amaçlı reducer fikri — repoda event store değildir
state = state.Apply(OrderPlaced(...));
state = state.Apply(InventoryReserved(...));
// Her Apply sürümlü, deterministik ve yeniden oynatılabilir olmalı.
Karar sınırıOutbox ile son durumu kaydedip event yayınlamak event-driven architecture'dır; event'ler kaydın kendisi olmadığı sürece Event Sourcing değildir.

Tartışma

“Order placed” olayından bir aggregate state'i türetin; ardından duplicate event, out-of-order, eski event schema ve projection rebuild senaryolarını tahtada yürütün. “Domain event var” iddiasını görünce storage/transaction/replay kanıtı aratın.

  • Stok rezervasyonu için invariant tek SKU/warehouse seviyesinde mi, birden çok aggregate arasında mı?
  • Olay kayıtlarında müşteri adresi bulunursa silme talebi nasıl karşılanır?
  • Yeni bir projection'ı baştan kurmak için hangi olayların, hangi sırada ve hangi hızda oynatılması gerekir?
Yaygın yanlışEvent log'a ek olarak güncel tabloyu da bağımsız, atomik olmayan biçimde yazmak iki source of truth üretir. Projection'ı türetilmiş ve yeniden kurulabilir kılın; transaction/Outbox ve version stratejisini belirleyin.
