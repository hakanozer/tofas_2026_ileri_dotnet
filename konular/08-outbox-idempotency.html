Transactional Outbox ve idempotent consumer

Veritabanı commit'i ile mesaj publish'ini tek transaction sanmayın. Crash window'larını ve tekrar teslimatın güvenli iş etkisine nasıl dönüştürüldüğünü inceleyin.

İş verisi + Outbox row aynı DB transaction'ı → relay → broker → inbox/dedup → consumer side effect

Dual-write neden güvenilmez?

İş verisini DB'ye kaydedip broker'a publish etmek iki bağımsız sistemde iki commit gerektirir. DB commit başarılıyken broker publish başarısız olursa state değişmiş, event kaybolmuştur. Publish başarılı olup DB commit fail ederse tüketici var olmayan state'i işler. DB transaction'ını açık tutup ağ üzerinden broker transaction'ıyla birleştirmek genellikle dağıtık XA/2PC ve availability/operasyon maliyeti doğurur; transaction outbox ise iş verisi ve publish niyetini aynı yerel DB transaction'ına yazar.

Relay, pending satırları broker'a en az bir kez gönderir, başarı sonrası delivered işaretler. Relay broker confirm aldıktan hemen sonra, DB'de delivered işaretlemeden çökebilir; bu nedenle duplicate yayın normaldir. Outbox kayıp mesaj riskini azaltır; consumer idempotency olmadan exactly-once business effect sağlamaz.

Projede Outbox ve Saga state'i

OutboxDbContext, MassTransit InboxState/OutboxState/OutboxMessage ve saga state entity'lerini outbox schema'sına map ediyor. Program.cs MassTransit EF Core Outbox'ı PostgreSQL ve RabbitMQ ile yapılandırıyor; saga state machine mesajlarıyla aynı DbContext'i paylaşıyor. Bu yaklaşımın kritik iddiası: saga state değişimi ve bus outbox message aynı transaction'a enlist edilir.

Deploy notuOrchestrator'da Database.MigrateAsync() host startup'ında koşuyor; kod çevresindeki yorum “dev only” dese de koşul environment kontrolüyle sınırlandırılmamış. Üretimde migration'ı ayrı, kontrollü deploy job'ına taşıyın; birden fazla replica'nın aynı anda schema migration yarışı ve uygulama hesabına fazla DDL yetkisi riskini değerlendirin.

Outbox polling interval, indeks, batch size, transaction duration, lock skip-locked davranışı, cleanup/retention ve broker confirm timeout'u ölçülmelidir. Çalışmayan relay için oldest pending age ve queue growth alarmı ekleyin. Outbox tablo büyümesini izleyin; kritik kayıtları audit ihtiyacıyla erken silmeyin.

Idempotency: tekrar teslimatın iş etkisini tekilleştirme

Idempotent consumer aynı mesajı birden çok kez almasına rağmen aynı iş sonucunu üretir. Dedupe key çoğunlukla message ID, operation ID veya iş anahtarı + aggregate version olur; key'in tenant/context kapsamı ve retention süresi tanımlıdır. Consumer önce processed-message kaydı ve domain etkisini tek DB transaction'ında yazar; unique constraint yarışları deterministik hale getirir. Yan etki başka sistemdeyse o sisteme idempotency key ile çağrı yapın veya ikinci bir Outbox üretin.

// Kavramsal şema: unique constraint duplicate yarışını DB seviyesinde önler.
CREATE TABLE processed_messages (
    consumer_name text NOT NULL,
    message_id uuid NOT NULL,
    processed_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (consumer_name, message_id)
);

Idempotency key'i payload hash'ine indirgemek semantik olarak farklı iki isteği yanlış birleştirebilir. Inbox retention, broker retention ve en uzun redelivery/replay süresiyle uyumlu olmalıdır. “Exactly once” broker özelliği, dış servis çağrısı, DB transaction ve yeniden başlatma dahil bütün iş akışını otomatik olarak garanti etmez.

Retry ve hata sınıflandırması

Transient connection error için bounded exponential backoff+jitter; validation/business rejection için retry değil, terminal event/rejection; poison payload için quarantine/DLQ. MassTransit consumer retry policy'lerinde in-memory retry sırasında delivery lock/broker resource'larının elde tutulma süresine dikkat edin; uzun backoff için delayed redelivery/scheduler modeli daha uygun olabilir. Polly, EF execution strategy ve broker retry aynı operation'a bindirilirse deneme sayısı katlanabilir. Tek bir end-to-end retry budget ve operation correlation ID belirleyin.

Kod yürüyüşü: Saga state ile Outbox mesajı aynı DB sınırında

Dual-write (iki ayrı sistemde ayrı commit) aralığını kapatmak için MassTransit EF Outbox mesaj kaydını saga/business state ile aynı PostgreSQL transaction'ında saklar; arka plan delivery service broker'a yollar. Bunun garantisi yalnız doğru DbContext/transaction pipeline'a bağlı publish'ler için geçerlidir.

// BackgroundOrchestrator/Program.cs — repodaki kayıt
x.AddEntityFrameworkOutbox<OutboxDbContext>(o =>
{
    o.QueryDelay = TimeSpan.FromSeconds(1);
    o.DuplicateDetectionWindow = TimeSpan.FromMinutes(5);
    o.UsePostgres();
    o.UseBusOutbox();
});

UseBusOutbox publisher'ı DB transaction'a bağlar; consumer inbox duplicate detection uygular. Broker confirm alındıktan, delivered state DB'ye yazılmadan önce process çökmesi halinde yeniden publish mümkündür. Bu nedenle Outbox teslimatı at-least-once'dır; consumer side effect'i de idempotent olmalıdır.

Repo'da OutboxDbContext MassTransit'in inbox/outbox/saga tablolarını map ediyor. Telemetry store'daki ON CONFLICT (device_id, timestamp_ms) DO NOTHING doğal anahtarla replay'i tekilleştirir; bu, message inbox değil, storage upsert idempotency'sidir. [DbContext](../src/Services/Orchestrator/BackgroundOrchestrator/Persistence/OutboxDbContext.cs), [registration](../src/Services/Orchestrator/BackgroundOrchestrator/Program.cs) ve [telemetry store](../src/Services/Telemetry/TelemetryStreamProcessor/Storage/NpgsqlTelemetryStore.cs) rollerini ayırt edin.

Operasyonel borçOutbox backlog/oldest age, delivery attempt, lock wait, table growth, cleanup retention ve poison event alarmı olmadan tablo sessizce büyür. Inbox dedupe retention broker replay/idempotency penceresinden kısa olursa eski duplicate yeniden işlenebilir.

Tartışma

Tahtada üç çökme anını işaretleyin: DB commit'ten önce, DB commit sonrası publish öncesi, broker confirm sonrası delivered işaretleme öncesi. Her durumda Outbox ve inbox'ın neyi çözdüğünü, neyi çözmediğini katılımcılara açıklatın.

  • Outbox tablosunun oldest row yaşı büyüyor ama API 200 dönüyor: kullanıcı etkisi ve alarmınız ne?
  • Mesajı 30 gün sonra replay ediyorsanız 7 gün sonra temizlenen inbox duplicate side effect yaratır mı?
  • Consumer email gönderiyor ve ardından DB commit ediyorsa hangi idempotency stratejisi email sağlayıcısıyla uygulanabilir?
