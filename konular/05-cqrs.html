CQRS neyi ayırır?

Command state değiştirmeyi talep eder; query state okumalı ve yan etkisiz olmalıdır. En hafif biçimde aynı veritabanı ve model üzerinde farklı handler/yetki/pipeline kullanılır. Daha ileri biçimde write modeli ve read projection ayrı şemalara veya depolara ayrılır. CQRS, otomatik olarak iki microservice, iki veritabanı veya Event Sourcing anlamına gelmez. Amaç, yazma tutarlılığı kuralları ile okuma performansı/şeklinin farklı değişim ihtiyaçlarını izole etmektir.

Command request'i “iş emri”dir; endpoint'ten gelen DTO'yu direkt EF entity'ye bağlamak yerine doğrulama ve idempotency key gibi transport ayrıntıları kontrollü taşıyın. Aggregate invariant'ı handler'da if/else olarak dağıtmak yerine domain davranışında koruyun. Query, liste ekranına uygun projection döndürebilir; entity graph'ını gereksiz yüklememelidir.

Projede karşılık: CQRS pipeline ve cache

GetInventoryAvailabilityQuery cacheable query sözleşmesini; CacheAsideBehavior ise MediatR pipeline üzerinden cache-aside, JSON serialization ve distributed single-flight kilidini gösteriyor. Bu kod gerçek iş mantığının tamamı değildir; doğrudan CQRS pipeline örneğidir. Cache key'de tenant, locale, authorization scope ve query variation unutulursa kullanıcılar arası veri sızıntısı oluşabilir.

Handler'a verilen CancellationToken'ı DB ve dış servis çağrılarına aktarın. Cache miss'te kilit alınamaması için fallback davranışı var; bu degrade yolu DB'ye eşzamanlı yük bindirebilir. Kilit timeout'u, maksimum bekleme ve fallback concurrency limit'i üretim profilinde gözlemlenmelidir. Invalidation olaylarının yalnızca uygulama belleğinde kalması, çoklu replica'da stale read üretir.

// Projede ICacheableQuery için kullanılan sözleşme mantığı
public interface ICacheableQuery
{
    string CacheKey { get; }
    TimeSpan? AbsoluteExpiration => TimeSpan.FromMinutes(5);
    TimeSpan? SlidingExpiration => null;
}

Ayrı read model: tutarlılık sözleşmesini açıkça kurun

Read projection async güncellenirse komut sonrası query eski state görebilir. Ürünün kabul ettiği gecikmeyi p95/p99 ve iş kuralı cinsinden tanımlayın. Kullanıcıya “işlem alındı” yanıtı, projection watermark/cursor'ı veya command response'ta güncel aggregate snapshot'ı seçenek olabilir; her ek mekanizma karmaşıklık yaratır. Read-your-writes gerekiyorsa sadece CQRS adını vermek çözüm değildir.

Projection consumer'ı replay edilebilir, idempotent ve checkpoint'li olmalıdır. Projection bozulduğunda kaynak veri üzerinden yeniden kurulabilmesi gerekir. Read model güncellemesi başarısızsa DLQ, lag metric, repair runbook ve schema rollout planı belirlenmelidir. Event Sourcing kullanılmasa bile Outbox ile yayınlanan integration event projection besleyebilir.

Ne zaman kullanmamalı?Basit CRUD, düşük okuma/yazma asimetrisi ve tek model yeterliyse ayrı handler ve projection katmanı gereksiz bilişsel/operasyonel yük olur. CQRS'yi sadece her endpoint'e Command/Query sınıfı ekleme törenine indirgemeyin.

Kod yürüyüşü: cacheable query'nin uçtan uca sözleşmesi

Repodaki GetInventoryAvailabilityQuery, okuma isteğini MediatR request'inden ayırır ve cache politikasını query'nin üzerinde bildirir. Sınıfta önce bu DTO'yu, sonra CacheAsideBehavior'ın pipeline sırasını izleyin: hit ise handler çalışmaz; miss ise distributed lock (replikalar arası tek-yükleme kilidi) alınır, cache tekrar okunur, ardından handler çağrılır.

// Inventory.Application/Queries/GetInventoryAvailabilityQuery.cs
public sealed record GetInventoryAvailabilityQuery(string Sku)
    : IRequest<InventoryAvailabilityResponse>, ICacheableQuery
{
    public string CacheKey => $"inventory:availability:{Sku}";
    public TimeSpan? AbsoluteExpiration => TimeSpan.FromSeconds(30);
    public TimeSpan? SlidingExpiration => null;
}

Asıl çözülen problem: sık okunan availability sorgusunun her istekte DB'ye gitmesini ve cache stampede'i (aynı miss'te eşzamanlı çok sayıda pahalı yükleme) azaltmak. 30 saniyelik TTL tazelik garantisi değil, stale-data penceresi kararıdır. Rezervasyon komutunun başarısı cache'den türetilmemeli; stok ayırma invariant'ı kalıcı store/transaction tarafında korunmalıdır.

Repo uyarısı: Cache key yalnızca SKU içerir. Eğer tenant/region/authorization aynı SKU için farklı görünüm üretiyorsa key'e bu boyutlar eklenmeli; aksi halde tenant'lar arası yanlış cache paylaşımı olabilir. [Query](../src/Services/Inventory/Inventory.Application/Queries/GetInventoryAvailabilityQuery.cs), [cache behavior](../src/BuildingBlocks/Shared.Kernel/Caching/CacheAsideBehavior.cs) ve [invalidation handler](../src/BuildingBlocks/Shared.Kernel/Caching/CacheInvalidationHandler.cs) birlikte açılmalı.

Hata anıRedis/lock arızasında davranış freshness, availability ve DB kapasitesi arasında tercihtir. Fail-open origin'e yük bindirir; fail-closed sorguyu keser. Timeout, fallback concurrency limit'i, hit/miss/lock wait metriği ve cache invalidation lag olmadan “cache eklendi” başarı ölçütü değildir.

Tartışma

Bir availability ekranı query'sini ve rezervasyon command'ini yan yana tasarlatın. Hangi veri stale olabilir, hangisi transaction içinde kesin olmalı? Ardından cache key'e tenant eklemeyi, cache write fail olduğunda isteğin ne yapacağını ve invalidation'ın outbox üzerinden nasıl yayıldığını tartıştırın.

  • Command başarıyla commit oldu ama projection 20 saniye geride: kullanıcıya hangi API semantiğini sunarsınız?
  • Cache miss storm'u DB kapasitesini aşıyorsa kilit, jitter TTL, stale-while-revalidate ve rate limit arasında nasıl seçim yaparsınız?
  • Yeni bir read model'i geriye dönük oluşturmak için hangi authoritative kaynağa ihtiyacınız var?
