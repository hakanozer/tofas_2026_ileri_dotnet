Sorgu performansında doğru sırayla ilerleyin

Önce SQL'i ve execution plan'ı görün; sonra row count, index selectivity, network round-trip, result size, lock wait ve allocation ölçün. Read-only query'de DTO projection + AsNoTracking entity materialization/change tracking'i azaltabilir. Include graph'ı N+1'i önleyebilir ama cartesian explosion/çok büyük result üretebilir; split query ek round-trip ve tutarlılık penceresi getirir. Pagination için offset yüksek sayfalarda pahalıdır; keyset pagination sıra/filtre anahtarı ve stable sort gerektirir. SQL parameterization güvenlik için default'tur; dynamic identifier whitelist ile ayrı yönetilir.

DbContext kısa ömürlü, request/unit-of-work scoped olmalıdır; aynı context üzerinde paralel operation çalıştırmayın. EF context pooling ve Npgsql connection pooling farklı seviyelerdir; context pooling'de tenant/state temizliği ve connection pool limit'leri kontrol edilmelidir. Raw SQL/bulk COPY hot path'te faydalı olabilir ama EF change tracker'dan kaçırdığı invariant, transaction ve observability yükünü uygulamaya taşır.

Transaction, concurrency ve Outbox

EF Core SaveChanges varsayılan transaction sınırında birden çok tracked change'i atomik yazar; birden fazla servis veya broker'ı kapsamaz. PostgreSQL unique constraint, row lock, isolation level ve xmin concurrency gibi mekanizmalar iş kuralına göre seçilir. Optimistic concurrency conflict'i “hata yok, retry” değildir: operation state'i yeniden yükleyip domain kararını tekrar değerlendirmek gerekir. Pessimistic lock throughput'u/queueing'i etkiler; lock order ve transaction süresi deadlock riskini belirler.

OutboxDbContext saga state için PostgreSQL xmin shadow property'yi concurrency token yapıyor ve MassTransit outbox entity'lerini aynı context'e map ediyor. Orchestrator'ın EF retry kapalı bırakma notu, transport retry ile nested retry'nin duplicate/conflict üretme riskini anlatıyor. Bu etkileşim provider ve MassTransit sürümüne göre integration test edilmelidir; genel kural olarak tüm retry'leri kapatın demek değildir.

Migration ve schema lifecycle

Üretimde uygulama startup'ında migration çalıştırmak rollout race, izin genişliği ve geri alma belirsizliği yaratabilir. Migration job'ı ayrı kimlikle çalıştırın; expand/contract ile önce geriye uyumlu kolon ekleyip writer/reader'ları kademeli geçirerek eski alanı en son kaldırın. Büyük tablo index'i, lock, backfill ve replication lag için online migration planı gerekir. Rollback çoğu zaman schema down değil, forward-fix'tir.

Connection pool, max concurrent request ve DB max connection arasında kapasite bütçesi kurun. İstek yoğunluğu arttığında EF connection pool timeout'u çoğu zaman DB CPU değil, uzun transaction/çok fazla replica işaretidir. Query timeout, command cancellation ve DB statement timeout birbiriyle koordine edilmelidir.

Uygulamalı inceleme

  1. Temsili liste query'sini projection + deterministic keyset pagination olarak tasarlayın.
  2. Query SQL'i, execution plan, index hit ve p95'i baseline alın.
  3. Tracking/Include/split query alternatiflerini aynı data volume ile kıyaslayın.
  4. İki eşzamanlı saga update'inde concurrency exception ve idempotent retry davranışını doğrulayın.
  5. Outbox backlog ve migration deploy'una runbook/SLO yazın.

Bu repoda Order/Inventory domain veri akışı tam bir EF business repository olarak uygulanmış değildir; Outbox persistence gerçekçi örnek, telemetry store Npgsql bulk upsert kullanır. Bu ayrımı “projede EF performans laboratuvarı hazır” diye genellemeyin.

Kod yürüyüşü: DbContext, provider retry ve kalıcılık sınırı

Repoda iş domain'i için tamamlanmış bir EF Core repository yok; EF Core 10 en görünür biçimde Orchestrator'ın Saga/Outbox persistence'ında kullanılıyor. Telemetry yolu ise EF yerine Npgsql bulk COPY + staging/upsert yapıyor. Bu ayrımı baştan kurun: performans örneğini tüm veri erişim şekillerine genellemeyin.

// BackgroundOrchestrator/Program.cs — gerçek EF provider kaydı
builder.Services.AddDbContext<OutboxDbContext>(options =>
{
    options.UseNpgsql(builder.Configuration.GetConnectionString("Postgres"), npgsql =>
    {
        npgsql.MigrationsHistoryTable("__ef_migrations", "outbox");
        // EnableRetryOnFailure bilerek etkin değil:
        // MassTransit consumer/outbox retry ile üst üste binmesin.
    });
});

Bir LINQ query'de önce projection yapın, read-only sorguda AsNoTracking değerlendirin, pagination'ı DB tarafında uygulayın ve SQL/index planını inceleyin. Ancak retrying execution strategy transaction'ı yeniden çalıştırabilir; dış side effect'i aynı delegate içine koymak duplicate e-posta/mesaj üretir. Outbox akışında retry sorumlulukları koordine edildiği için mevcut proje EF retry'ını yorum olarak kapatıyor.

[Orchestrator Program.cs](../src/Services/Orchestrator/BackgroundOrchestrator/Program.cs), [OutboxDbContext](../src/Services/Orchestrator/BackgroundOrchestrator/Persistence/OutboxDbContext.cs) ve [telemetry bulk store](../src/Services/Telemetry/TelemetryStreamProcessor/Storage/NpgsqlTelemetryStore.cs) üzerinden compare/contrast yapın. `DbContext` request/operation scope'unda tutulmalı; singleton'a koymayın. N+1, cartesian explosion, overfetch, uzun transaction, eksik index ve concurrency token eksikliği production issue'larının temelidir.

Migration sınırıOrchestrator mevcut örnekte startup sırasında `Database.MigrateAsync()` yapıyor; yorumda bunun development için olduğu, production migration'ın explicit release adımında uygulanması gerektiği belirtilmiş. Çok replika aynı anda kalkarken startup DDL lock/permission riski vardır. Expand-contract (önce geriye uyumlu şema ekle, sonra kodu geçir, en son eski şemayı kaldır) rollout planı kullanın.

Tartışma

Tek bir LINQ query'nin oluşan SQL'ini gösterin. Katılımcılardan tahmin değil query plan üzerinden index önerisi isteyin. Sonra outbox polling ve saga update transaction'ında lock süresinin broker throughput'una etkisini bağlayın.

  • DbContext pooling tenant state'i tutuyorsa request'ler arasında nasıl sızıntı yaratabilir?
  • Read replica kullanımı hangi read-your-writes ve replication lag beklentisini bozar?
  • Migration rollback güvenli değilse release ve application rollback nasıl koordine edilir?
